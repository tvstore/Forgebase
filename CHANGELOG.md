# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html) once published.

## [Unreleased]

### Added

- Workspace skeleton (4 crates), CI, toolchain pin, cargo-deny config, contribution docs.
- Toolchain pinned to 1.99.1; MSRV (`rust-version`) 1.97.
- `forgebase-core`: DocType metadata model loaded from TOML with collected validation errors, identifier rules, dynamic `Value` model and document validation (full and partial update). New dependencies: `serde`, `toml`, `thiserror`, `rust_decimal`, `time`.
- Docs: M1 DB-layer spike result (ADR 0004 direction confirmed), owner decisions of 2026-10-28 (TOML, UUID v7, PostgreSQL floor 16, `time`, `rust_decimal`).
- `forgebase-db` (M1.2): connection pool (no TLS yet), embedded framework migrations (`fb_migration`, `fb_doctype`) with checksums and an advisory lock, and additive DocType schema sync with dry-run, conflict refusal and `lock_timeout`. Constraint and index names are chosen by PostgreSQL. Integration tests run against PostgreSQL 16 (`FORGEBASE_TEST_DATABASE_URL`; CI service container). New dependencies: `tokio-postgres`, `deadpool-postgres`; dev: `tokio`.
- Docs: owner decisions of 2026-10-28 on Int/Data/required/Decimal marked Accepted; M1.2 behavior recorded in architecture section 5 and the security model.
- `forgebase-db` (M1.3): document `insert`, `get`, `update` and `delete` on a pooled client or a caller-owned transaction. Names follow the DocType naming rule (random = the UUID v7, or a field value), `id` is a UUID v7 generated in the application, timestamps come from the database `now()`, `version` starts at 1 and counts updates, `owner` / `modified_by` record the actor. Values are bound parameters with explicit casts; unique violations, validation errors, missing documents and invalid actors have their own `DbError` variants. No permissions, concurrency check or renames yet. New dependencies: `uuid` (v7), `bytes`; `tokio-postgres` features `with-uuid-1` and `with-time-0_3`; `rust_decimal` feature `db-tokio-postgres` (in `forgebase-db` only).
- `forgebase-cli` (M1.3): the `forgebase` binary with `migrate [--dry-run]` and `doc insert|get|update|delete`, configured by `FORGEBASE_DATABASE_URL`, JSON in and out (Decimal as a string), exit code 0 / 1 / 2. New dependencies: `clap` (derive), `serde_json`, `tokio`; `time` features `parsing` and `formatting` (CLI only).
- `examples/doctypes/customer.toml` and a README quick start.
- Docs: M1 marked delivered (Done when M1.3 is merged); document CRUD rules in the architecture, CLI trust model in the security model, admission notes for `uuid`, `bytes`, `serde_json` and `clap`.
- M2.1, `forgebase-core`: Link fields (`type = "link"`, `target = "<doctype>"`; the value is the target document's name), `Registry::check_references` (every Link target must be in the registry; a self-link is allowed), `DefinitionError::UnknownLinkTarget` and `InvalidLinkTarget`, `ValidationError::LinkNotFound` and `ValidationError::field`.
- M2.1, `forgebase-db`: a Link column is `uuid` with an unnamed foreign key to the target's `id` (`ON DELETE RESTRICT`) and an index, created by schema sync in new phases (keys, then foreign keys, then indexes) so DocTypes that link to each other or to themselves sync in one run; new steps `AddForeignKeys` and `CreateIndex`; a missing or wrong foreign key (absent, other table, delete rule other than `RESTRICT`, or on a non-Link column) is a sync conflict (`Conflict::ForeignKeyMismatch`; a `NOT VALID` foreign key counts as wrong too), a missing index is an additive step; a Link to an unknown DocType is `DbError::InvalidMetadata`.
- M2.1, `forgebase-db`: document writes resolve Link names to ids (`FOR KEY SHARE`) and reads return names; `DbError::Conflict` (optimistic concurrency) and `DbError::LinkedDocumentExists` (a document that others link to cannot be deleted; the message names the linking DocType).
- M2.1, `forgebase-cli`: Link values are JSON strings; `doc update` and `doc delete` require `--version N`; the DocType loader reports Link targets that no file defines. `examples/doctypes/customer_group.toml` and a `customer_group` Link on the example customer.
- M2.2, `forgebase-core`: child tables. `FieldType::Table { target }` (`type = "table"`, `target = "<child doctype>"`; `required` means at least one row, `unique` is not allowed) and `DocType::is_child` (`is_child = true`: no `naming`, no Table fields, no `unique` fields, not a Link target, no CRUD of its own). `Registry::check_references` also checks that a Table target is a child DocType, that a Link target is not a child and that every child DocType is used by exactly one Table field; new `DefinitionError` variants (`InvalidTableTarget`, `UniqueTable`, `ChildWithNaming`, `ChildWithTable`, `ChildWithUnique`, `UnknownTableTarget`, `TableTargetNotChild`, `LinkToChild`, `UnusedChild`, `ChildSharedByTables`), `Registry::parent_of`, `DocType::column_fields` and `table_fields`. `Document::tables` and the new `Changes { values, tables }` hold the rows (`Row`); row problems are `ValidationError::InRow { field, row, error }` with the 1-based position.
- M2.2, `forgebase-db`: the table of a child DocType has `id`, `parent_id` (unnamed foreign key to the parent's `id`, `ON DELETE CASCADE`, plain index) and `idx` and no standard `name`, `owner`, `version` or timestamp columns; a Table field has no column. A missing, mistyped or wrongly ruled `parent_id` key is a sync conflict; a missing index is an additive step. `StoredDocument::tables` returns the rows in order; `insert` writes them with the document, `update` replaces the rows of the Table fields it names (an update of tables only is valid), `delete` removes them through the cascade. New `DbError` variants `UnknownDocType`, `ChildDocType` and `ChangedWhileReading`.
- M2.2, `forgebase-cli`: a Table field is a JSON array of row objects (input and output); the DocType loader reports child-table problems with the file name. `examples/doctypes/sales_order.toml` and `sales_order_item.toml`, and a README example with rows.
- M2.3, `forgebase-core`: lifecycle hooks. `forgebase_core::hooks` with the `DocTypeHooks` trait (default no-op methods `before_insert`, `validate`, `before_delete`; synchronous, no database access), `HookContext { doctype, actor, operation }`, `Operation` (`#[non_exhaustive]`) and `HookError`; `Registry::add_hooks` and `Registry::hooks` (hook sets run in registration order; an unknown or a child DocType is refused with the new `DefinitionError::UnknownHooksDocType` and `HooksOnChildDocType`). The module documentation has the pipeline order and a compile-tested example.
- M2.3, `forgebase-db`: the fixed lifecycle pipeline (hooks, validation, Links, naming, write) for insert, update and delete in one transaction; a hook error is the new `DbError::Hook { doctype, hook, message }` and rolls the whole operation back. Tests in `tests/lifecycle.rs`.
- Docs: [ADR 0009](docs/adr/0009-lifecycle-pipeline-and-hooks.md) (lifecycle pipeline and hooks); architecture section 6 now specifies the order per operation.
- M2.4, `forgebase-core`: docstatus and naming series. `DocType::submittable` (`submittable = true`; a definition error on a child DocType or together with field naming), `DocField::allow_on_submit` (a definition error on a DocType that is not submittable and on a Table field), `DocStatus` (`Draft`, `Submitted`, `Cancelled`; 0, 1, 2), `Naming::Series(SeriesPattern)` (`naming = { series = "INV-.YYYY.-.#####" }`) and the new module `forgebase_core::series` (`SeriesPattern::parse`, `prefix` and `render`: pure, validated when the DocType is loaded, a number wider than the `#` run is printed in full). `DocTypeHooks::before_submit` (`&mut Document`) and `before_cancel` (`&Document`) as default no-op methods, and `Operation::{Submit, Cancel, Amend}`. New `DefinitionError` variants: `InvalidSeriesPattern`, `ChildSubmittable`, `SubmittableWithFieldNaming`, `AllowOnSubmitNotSubmittable`, `AllowOnSubmitTable`.
- M2.4, `forgebase-db`: framework migration 0002 creates `fb_series` (`prefix text PRIMARY KEY`, `current bigint NOT NULL`). A submittable DocType's table has `docstatus smallint NOT NULL DEFAULT 0` and a nullable `amended_from text`; schema sync adds them to an existing table additively, reports drift as a conflict and reports them as `ColumnNotInMetadata` warnings when `submittable` is turned off. The new operations `submit`, `cancel` and `amend` (same transaction, savepoint, `expected_version` and actor handling as `update` and `delete`, each with a documented pipeline) and the rules by docstatus for `update` (a submitted document only changes `allow_on_submit` fields, a cancelled one not at all) and `delete` (not a submitted one). `StoredDocument` has `docstatus` and `amended_from`. Series naming takes the number from `fb_series` in the insert's transaction (gapless per rendered prefix, a rollback returns it; DocTypes sharing a prefix share the counter; the prefix is rendered with the UTC date of the transaction and bound). New `DbError` variants: `InvalidDocStatus`, `NotSubmittable`, `FieldLocked`, `AlreadyAmended`. Tests: `tests/docstatus.rs`, `tests/series.rs`, `tests/docstatus_schema.rs`.
- M2.4, `forgebase-cli`: `doc submit`, `doc cancel` and `doc amend` (`--version N` required, `--actor`, no data); the output of a submittable DocType has `docstatus` and `amended_from`. `examples/doctypes/sales_order.toml` is now submittable, uses the series `SO-.YYYY.-.#####` and has an `allow_on_submit` field `remarks`; the README walks through insert, submit, cancel and amend.
- Docs: architecture sections 3, 5 and 6 (docstatus and naming series implemented, with the M2.4 implementation details), feature matrix, security model, [ADR 0009](docs/adr/0009-lifecycle-pipeline-and-hooks.md) implementation details for M2.4, M2 marked Done.
- M3.1, `forgebase-db`: framework migration 0003 (`fb_user`, `fb_user_role`, `fb_session`, `fb_api_token`, `fb_login_failure`) and the `forgebase_db::auth` module: `create_user`, `set_password`, `set_enabled`, `add_role`, `remove_role`, `login`, `validate_session`, `check_csrf`, `logout`, `create_api_token`, `validate_api_token`, `revoke_api_token`, with `AuthUser`, `LoginSession`, `ApiTokenSecret` (secrets redacted in `Debug`) and `AuthError`. Argon2id passwords, opaque server-side sessions (7 days absolute, 24 hours idle, a new session on every login), SHA-256 digests of tokens computed by PostgreSQL, a uniform login error, and per-username lockout (5 failures, 15 minutes; the failure accounting commits even when the login fails, so call `login` on a pooled client). New dependencies: `argon2` 0.6 (features `alloc`, `password-hash`) and `getrandom` 0.4; `tokio` is now a normal dependency of `forgebase-db`.
- M3.1, `forgebase-cli`: `user create|set-password|add-role|remove-role|disable|enable` (passwords from the first line of standard input only) and `token create|revoke` (`create` prints `key:secret` once).
- Docs: [ADR 0010](docs/adr/0010-authentication-and-sessions.md) (authentication and sessions); security model (authentication implemented, three open questions answered), dependency evaluation (admission notes for `argon2` and `getrandom`, open question 9), architecture (auth tables, CLI), M3 marked In progress, and the owner decision of 2026-10-29 on naming series prefixes (option (a): DocTypes sharing a prefix share one counter) recorded as Accepted.
- M3.2, `forgebase-core`: the permission model, new module `forgebase_core::permission`: `PermissionRule`, `Right` (`Read`, `Write`, `Create`, `Delete`, `Submit`, `Cancel`, `Amend`), `Caller` (`User { username, roles }` or the trusted `System { actor }`), `Access` (`All`, `OwnerOnly`, `Denied`), the constant `ADMINISTRATOR` and `evaluate`, the one pure function that decides access. `DocType::permissions` is loaded from `[[permissions]]` (`role`, the seven rights and `if_owner`, all `false` by default; unknown keys rejected). New `DefinitionError` variants: `InvalidPermissionRole`, `EmptyPermissionRule`, `PermissionNeedsSubmittable`, `DuplicatePermissionRule`, `ChildWithPermissions`. The role name rule is shared with `forgebase_db::auth` (`check_role_name`).
- M3.2, `forgebase-db`: every document operation enforces the permissions of the DocType. Read access is applied in SQL (`AND "owner" = $n` for an `if_owner` read, also in the locking reads), so a document the caller cannot read is `None` (`get`) or `NotFound` (everything else), also for a stale version (never `Conflict`) and as a Link target (`LinkNotFound`); a right that depends on no document is the new `DbError::PermissionDenied { doctype, right }`; `LinkedDocumentExists::referenced_by` is `None` unless the caller can read the linking DocType ([ADR 0011](docs/adr/0011-permission-model-phase-1.md), owner decisions 2 and 9). New `forgebase_db::list` with the typed `ListQuery`, `Filter`, `FilterOp` (`=`, `!=`, `<`, `<=`, `>`, `>=`, `in`, `is null`, `like`), `Sort`, `column_type` and the constants `DEFAULT_LIMIT` (20), `MAX_LIMIT` (500) and `MAX_IN_VALUES`; a new error `DbError::InvalidQuery`. `AuthUser::caller()` builds the `Caller` of an authenticated user; `forgebase_db::Caller` re-exports the type. Tests: `tests/permissions.rs` (the authorization matrix, `if_owner`, deny by default, union of roles, decision 9, hooks) and `tests/list.rs` (every operator, sorting and paging, limits, unreadable rows never listed, hostile input).
- M3.2, `forgebase-cli`: `forgebase doc list DOCTYPE [--filter JSON] [--sort FIELD[:desc]]... [--limit N] [--offset N]` prints a JSON array. The `doc` commands run as the trusted system context (no permission rules apply to them). Links already stored on a document are kept on `update` and `submit` when the caller cannot read their targets (per field and per child table; a new or changed value, a value a hook sets and every `amend` are checked): see [ADR 0011](docs/adr/0011-permission-model-phase-1.md), item 6.
- M3.2 follow-ups, tests: the kept rule is scoped per Link field and per child table, and a `before_submit` hook cannot link to a document the caller cannot read (`forgebase-db/tests/permissions.rs`).
- Docs: [ADR 0011](docs/adr/0011-permission-model-phase-1.md) (permission model, phase 1); security model (authorization and query enforcement implemented; the Link resolution and read-only role questions answered), architecture, feature matrix, milestones, `[[permissions]]` in the example DocTypes and a README section.

### Changed

- **Breaking (0.x):** `forgebase_db::insert`, `get`, `update` and `delete` take `&mut impl GenericClient` (was `&impl GenericClient`) and the `&Registry` plus the DocType **name** (`&str`) instead of `&DocType`; `update` takes `&Changes` instead of a map of values. Each call runs in `client.transaction()` (a transaction on a pooled client, a savepoint inside a caller's transaction), so a document and its rows are written atomically on a pooled client too, the Link `FOR KEY SHARE` lock now lasts until the write is done, and a failed call no longer aborts a caller-owned transaction.
- **Breaking (0.x):** `forgebase_core::document::validate` and `validate_update` take the `&Registry` as first argument (to find child DocTypes), `validate_update` takes `&Changes`; `Document` has a new field `tables`, `DocType` a new field `is_child`, `StoredDocument` a new field `tables` (struct literals need them); `FieldType::Table`, the new `DefinitionError`, `ValidationError::InRow` and `DbError` variants need new arms in exhaustive matches; `parse_values` in the CLI became `parse_input`. A DocType that switches between child and not child is a schema sync conflict.
- **Breaking (0.x, accepted by the owner 2026-10-28):** `forgebase_db::update` and `forgebase_db::delete` take an `expected_version: i64` argument (after `name`) and fail with `DbError::Conflict` when the stored version differs; `forgebase doc update` and `doc delete` require `--version N`. Before this change the last writer won.
- `forgebase_core::meta::FieldType` has a new variant `Link { target }` and `forgebase_core::document::ValidationError` (`LinkNotFound`), `forgebase_core::meta::DefinitionError` (`UnknownLinkTarget`, `InvalidLinkTarget`), `forgebase_db::Step`, `Conflict` and `DbError` have new variants (the enums are not `non_exhaustive`: exhaustive matches in other code need new arms). `Registry::add` still checks one DocType only; call `Registry::check_references` after loading all DocTypes.
- Docs: all seven M2 owner decisions of 2026-10-28 recorded as Accepted; M2 marked In progress.
- **Behaviour change (0.x), M2.3:** `forgebase_db::update` now reads the stored document first (row lock `FOR NO KEY UPDATE`) and merges the changes into it, so the `validate` hooks and the framework validation see the **whole** document: a stored value that is no longer valid (a required field that is null in the row) is now reported by an update that does not touch it. It writes every column field and replaces only the tables whose rows differ from the stored ones (a table that is unchanged keeps its row ids). `NotFound` and `Conflict` are now reported before validation (a stale update with invalid changes returns `Conflict`, not the validation errors). `update` still always bumps `version` (an explicit save), and only an empty `Changes` is `NoChanges`. `delete` reads the document with `FOR UPDATE` first, for `before_delete`.
- **Breaking (0.x), M2.3:** `forgebase_db::delete` takes an `actor: &str` as its last argument (validated like for `insert` and `update`; an empty one is `DbError::InvalidActor`), so `HookContext::actor` is a `&str` (not an `Option`) for every operation. `forgebase doc delete` accepts `--actor NAME` (default `cli`), like `doc insert` and `doc update`.
- **Breaking (0.x), M2.3:** `forgebase_core::meta::Registry` no longer implements `PartialEq` and `Eq` (it holds hook trait objects); its `Debug` output prints the number of hook sets per DocType. `DbError` and `DefinitionError` have new variants (`Hook`; `UnknownHooksDocType`, `HooksOnChildDocType`): exhaustive matches need new arms.
- **Breaking (0.x), M2.3:** `forgebase_core::document::validate_update` was removed: `forgebase-db` now validates the whole merged document with `validate` (nothing else used it). `Changes` stays, as the input of `forgebase_db::update`.
- **Breaking (0.x), M2.4:** `forgebase_core::meta::DocType` has a new field `submittable` and `DocField` a new field `allow_on_submit` (struct literals need them); `Naming` has a new variant `Series` and `forgebase_core::hooks::Operation`, `DefinitionError` and `forgebase_db::DbError` new variants (exhaustive matches need new arms; `Operation` is `#[non_exhaustive]`); `forgebase_db::StoredDocument` has the new fields `docstatus` and `amended_from`.
- **Breaking (0.x), M2.4:** `amended_from` is now a reserved field name (like `docstatus`, which already was): a DocType with a field of that name is refused when it is loaded. `DocTypeHooks` gained two default methods, so existing hook sets compile unchanged; but `validate` now also runs on submit and on amend, and `before_insert` on amend, so a hook that assumes `validate` only sees insert and update should check `ctx.operation`.
- **Breaking (0.x), M2.4:** there is a second framework migration (0002, `fb_series`); `forgebase migrate` applies it (a database at migration 1 is upgraded). `forgebase migrate` output now lists two migrations on a fresh database. `delete` of a submitted document and `update` of a cancelled one are refused (`DbError::InvalidDocStatus`), and the example `sales_order` DocType is now submittable with a naming series (its names are `SO-<year>-<number>`, no longer UUIDs).
- **Behaviour change (0.x), M3.1:** there is a third framework migration (0003, the auth tables); `forgebase migrate` applies it and lists three migrations on a fresh database (a database at migration 2 is upgraded).
- **Breaking (0.x), M3.2:** the `actor: &str` argument of `forgebase_db::insert`, `update`, `delete`, `submit`, `cancel` and `amend` is now `caller: &Caller`, and `get` takes a `caller` as its last argument. Use `Caller::system("cli")` for the old, unchecked behaviour (the system context bypasses the permission rules and records its actor as before) or `AuthUser::caller()` for a user. `forgebase_core::meta::DocType` has a new field `permissions` (struct literals need it); `DefinitionError` and `forgebase_db::DbError` have new variants (exhaustive matches need new arms). `HookContext::actor` is now the caller's name (the username of a user).
- **Behaviour change (0.x), M3.2:** a DocType without `[[permissions]]` is closed to every caller except an `Administrator` and the system context (deny by default). The example DocTypes got rules for `Sales User` and `Sales Manager`; the `forgebase doc` commands are unaffected (system context).
- **Fix (M3.1 follow-ups):** the login failure window is now inclusive (`>=`: a failure exactly 15 minutes after the previous one still counts), which makes the code agree with "at most 15 minutes" in the docs; a test covers a failure 14 minutes 59 seconds after the previous one. Doc fixes: the lockout cleanup condition now matches ADR 0010, `create_api_token` refusing a disabled user is no longer listed as a known limit, and the long doc comment of the CLI binary is wrapped.
- M3.3, `forgebase-http`: the HTTP API on axum. `POST /api/v1/login` and `/logout`; `GET|POST /api/v1/resource/{doctype}`, `GET|PATCH|DELETE /api/v1/resource/{doctype}/{name}` and `POST .../submit|cancel|amend`, with `filters`, `sort`, `limit` and `offset` for lists; optimistic concurrency through `version`. Per request: `Host` validation first (`FORGEBASE_ALLOWED_HOSTS`), then authentication (`Authorization: token <key>:<secret>` wins over the `fb_session` cookie; one uniform 401), then the CSRF header `X-Forgebase-CSRF` for cookie-authenticated requests that are not `GET`; the user becomes a `Caller::User` (never `Caller::System`). Session cookie `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=604800` (no `Secure` only with `FORGEBASE_DEV_INSECURE_COOKIES=1`). No CORS headers. Every error, extractor rejections included, is the envelope `{"error": {"code", "message", "details"?}}` with stable codes; internal errors are generic and logged to standard error. Concurrent logins are bounded (default 8 and at most half of the pool size, excess 503 with `Retry-After`); a repeated or unknown query parameter is 400 `invalid_query`, a request body is limited to 1 MiB. Library API: `AppConfig`, `AppState`, `router`, `serve`. Tests: `forgebase-http/tests/{auth,resources,protocol}.rs`.
- M3.3, `forgebase_http::json`: the JSON mapping moved from the CLI into `forgebase-http` and is shared by the CLI and the HTTP API (new `input_from_json`; the filter and sort error messages no longer mention `--filter` and `--sort`).
- M3.3, `forgebase-cli`: `forgebase serve --doctypes DIR` (`FORGEBASE_LISTEN`, default `127.0.0.1:8000`; `FORGEBASE_ALLOWED_HOSTS`, default `localhost,127.0.0.1`; `FORGEBASE_DEV_INSECURE_COOKIES=1` with a startup warning), graceful shutdown on Ctrl-C or SIGTERM (10 s grace, a second signal exits at once), `FORGEBASE_ALLOWED_HOSTS` entries with a port are refused, no migrations. New dependencies: `axum` 0.8.9 (features `http1`, `json`, `query`, `tokio`; 22 new packages in total, all MIT, Apache-2.0 or BSD-3-Clause compatible) and the dev-dependencies `tower` (`util`) and `deadpool-postgres` (already in the workspace); `tokio` features `net` and `sync` (`forgebase-http`) and `net` and `signal` (`forgebase-cli`). No `tower-http`, no `cookie` crate.
- Docs: M3.3 in architecture (sections 1, 5 and 7: routes, request pipeline, cookie, error envelope), security model (the HTTP layer; the CORS, Host and login concurrency questions answered; every required negative test mapped to its tests), dependency evaluation (admission notes), feature matrix, [ADR 0005](docs/adr/0005-http-stack.md) implementation note, README (HTTP API section with `curl` examples), and M3 marked Done with its exit-criteria evidence.
