# Feature matrix

Compares Frappe Framework capabilities with Forgebase's plan. Research date: 2026-10-28. Design details are in [architecture](architecture.md); milestones in [milestones](milestones.md).

## How to read this

**Evidence labels** (for the "Frappe behavior" column):

| Label | Meaning |
|---|---|
| `Source-indexed` | Backed by a web-search result from an official Frappe domain; the URL is given. Search summaries are second-hand paraphrases, so wording and version scope may differ from the live page. |
| `Unverified` | General knowledge only. Must be confirmed before anyone relies on it. |

There is **no `Verified-fetched`** entry yet: `docs.frappe.io` could not be fetched directly from the research environment (the fetch was blocked by the sandbox with ENOTFOUND; only that domain was tried), so no page was read in full. To promote a claim, open the URL and confirm. Open verification questions are listed at the end.

**Forgebase status values:**

| Status | Meaning |
|---|---|
| Planned (Mx) | Intended for milestone Mx. Still **Proposed** until the owner accepts the plan for that milestone. |
| Intentional difference | Forgebase deliberately does it differently from Frappe. |
| Undecided | Options exist; decision deferred. A milestone is noted where the approved plan ties it; otherwise: decide when the related milestone is planned. |
| Not a priority | May be considered later; no plan. |
| Out of scope | Will not be built. |

Frappe URLs below are shortened: `fw/` = `https://docs.frappe.io/framework/user/en/`, `fwo/` = `https://frappeframework.com/docs/user/en/`, `erp/` = `https://docs.frappe.io/erpnext/`. Paths follow these prefixes as listed in the research source; where a URL does not follow a prefix, the full URL is written out.

| Webhooks | A `Webhook` DocType (DocType, event, URL, headers, optional Jinja payload and condition); sent by a background job; request signed with an optional secret (`X-Frappe-Webhook-Signature`, HMAC-SHA256 of the body, base64). | Source-indexed: `fw/guides/integration/webhooks` | Intentional difference; implemented in M9.2 | A table `fb_webhook` per site and `forgebase webhook add\|list\|disable\|enable\|remove\|rotate-secret\|test`, no desk screen. | Data import | Data Import tool: upload CSV or Excel, map columns, validate, import in the background, update existing records; child tables in the same sheet. | Unverified (not read in this research) | Intentional difference; implemented in M9.3 | `POST /api/v1/import/{doctype}` (CSV or JSON; insert or an explicit upsert by `name`) needs **`import` and `create`** (and `write`); every row goes through the normal pipeline as the caller (hooks, validation, naming, permissions, webhooks); **all-or-nothing** in one transaction with a savepoint per row; `dry_run=1` reports every row's error and changes nothing; at most 10 000 rows and 16 MiB; the `csv` crate reads CSV. Child rows through JSON only. `forgebase data import`; the desk's Import page (validate, then import). No Excel, no column mapping, no background import ([ADR 0021](../adr/0021-import-and-export.md)). |
| Background jobs | Python RQ + Redis; `frappe.enqueue(...)`; queues short/default/long; `enqueue_after_commit`. | Source-indexed: `fw/api/background_jobs` | Implemented in M6.1 (queue, worker, retry, dead state, lease recovery, CLI) | Postgres `SKIP LOCKED` queue; hooks enqueue in the document's transaction (transactional outbox), so `enqueue_after_commit` needs no extra flag. One queue, no priorities; demonstrated by the example apps (M6.3: a log job enqueued from `before_submit` and `before_cancel`, and a job of an extension app); see [architecture, section 8](architecture.md#8-background-jobs-scheduler-realtime) and [ADR 0013](../adr/0013-jobs-scheduler-and-transactional-outbox.md). No Redis. |
| Scheduler | `scheduler_events` (hourly, daily, cron, ...) synced to Scheduled Job Type; long-running process enqueues jobs. | Source-indexed: `fw/api/background_jobs`, `fw/python-api/hooks` | Implemented in M6.2 | `App::schedule`: every N minutes (aligned to the Unix epoch), daily or weekly, UTC, no cron; demonstrated by the `sales` daily summary (M6.3); each schedule row claimed atomically by the worker, no leader, missed ticks not caught up; built-in clean-up jobs for finished jobs, login failures and expired sessions ([ADR 0013](../adr/0013-jobs-scheduler-and-transactional-outbox.md)). |
| Realtime | Node.js socket.io server fed via Redis pub/sub; `frappe.publish_realtime`. | Source-indexed: `fw/api/realtime` | Undecided | Deferred; decide when the related milestone is planned. Option: LISTEN/NOTIFY to SSE/WebSocket in the same binary. No Node, no Redis. |
| Desk | Metadata-driven admin SPA: list, form, report views; timeline. | Source-indexed: `fw/desk`, `fw/api/list` | Implemented in M4 (minimal) | Minimal generic list + form in React + TS, no UI library (Accepted 2026-10-29). Login, home and list view in M4.1; the form view with submit, cancel, amend and delete, and a Playwright smoke test in M4.2. | Reports | Report Builder (no-code), Query Report (SQL), Script Report (Python). | Source-indexed: `fw/desk/reports/report-builder`, `.../query-report`, `.../script-report` | Partly implemented: saved list views and the group-by summary (M8.3) and SQL query reports (M8.4, [ADR 0016](../adr/0016-query-reports-read-only-execution.md)); no report builder, script reports or export | Saved list views (private per user; shared views only by an Administrator) and a group-by summary with count, sum, average, minimum and maximum, through the permission-filtered list query, are implemented in M8.3 ([architecture, section 11](architecture.md#11-desk-reports-workflow)); **query reports (M8.4):** app-defined SQL compiled into the binary, run per role in a read-only transaction with a timeout and a row limit, with typed bound parameters and a parameter form and a sortable table in the desk; row-level rules do not apply inside a report; no CSV export (M9.3) and no charts; the SQL is checked at `migrate` ([ADR 0016](../adr/0016-query-reports-read-only-execution.md)); the `sales` example has the report "Sales by customer" ([guide](../guide/workflow-and-reports.md)); script reports: Out of scope ([architecture, section 11](architecture.md#11-desk-reports-workflow)). |

## Open verification questions

Taken from the research; each needs a direct read of the official page.

1. Exact controller hook order (`after_insert` vs `on_update`; `before_submit`, `before_cancel`, `on_trash`, `after_delete`).
2. Link validation on save, the delete-time link check, and whether any DB-level FK exists.
3. User Permission matching rules and interaction with If Owner and sharing.
4. DocShare model and interaction with role permissions.
5. Whether `/api/v2` exists and its shape.
6. Official PostgreSQL support status.
7. Amendment naming (`-1` suffix) and the `amended_from` chain.
8. Optimistic concurrency on save.
9. Atomic save of child rows and `idx` maintenance.
10. Full field-type list and DB column types.
11. Fixture sync conflict rules with site edits. **Answered (owner decision 10 of the M9 plan, 2026-10-30; [ADR 0022](../adr/0022-fixtures.md)):** a record is inserted if missing, updated only when the app's version of that record changed (a checksum per record), so site edits survive until then, and never deleted.
12. Per-site app installation and migrations across sites.
