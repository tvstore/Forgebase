# Security model

Status: **Proposed** unless stated; of the sections below identifier and value handling in `forgebase-db` (M1.2, M1.3, M2.1, M2.2), the trust note for the command-line tool, the storage side of authentication (M3.1, [ADR 0010](../adr/0010-authentication-and-sessions.md), Accepted) the role permission model with its enforcement and the list query (M3.2, [ADR 0011](../adr/0011-permission-model-phase-1.md), Accepted) and the HTTP layer (M3.3: cookies, CSRF, Host validation, no CORS, the login concurrency bound, the error envelope) are implemented. Multi-site isolation is not. Architecture context: [architecture](architecture.md). Frappe behavior referenced is labelled in the [feature matrix](feature-matrix.md). Changes to authentication, authorization or multi-site isolation are high-impact: they need Stage 1 planning and independent Stage 3 review per [AGENTS.md](../../AGENTS.md).

## Principles

- **Deny by default everywhere.** A DocType with no permission rules is inaccessible except to the `Administrator` role and the trusted system context (implemented in M3.2).
- **One enforcement point.** A single permission evaluator in `forgebase-core` (`forgebase_core::permission::evaluate`); no endpoint bypasses it (implemented in M3.2: every document operation of `forgebase-db` calls it).
- **Framework owns the dangerous parts.** Identifiers, SQL, transactions and sessions are handled by the framework, not by app code.
- **Secrets stay out of the data plane** (see Secrets).

## Authentication (milestone M3; storage side implemented in M3.1, [ADR 0010](../adr/0010-authentication-and-sessions.md))

| Mechanism | Design |
|---|---|
| Browser sessions | Opaque random token (32 bytes from the operating system, 64 hex characters). **Implemented (M3.1):** only the SHA-256 digest is stored in `fb_session`, with a CSRF token digest, the user, an absolute expiry (7 days) and an idle expiry (24 hours since last use); every login creates a new session; logout, password change and disabling the user delete sessions. **Implemented (M3.3):** carried in the cookie `fb_session=<token>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=604800` (`Secure` is omitted only with the explicit `FORGEBASE_DEV_INSECURE_COOKIES=1` development mode, which prints a warning); every cookie-authenticated request that is not `GET`/`HEAD` needs the session's CSRF token in the `X-Forgebase-CSRF` header (`check_csrf`, else 403 `csrf_failed`; the token is returned once by the login response). Logout (CSRF required) deletes the session and clears the cookie. |
| API tokens (machine clients) | **Implemented (M3.1; HTTP in M3.3):** sent as `Authorization: token <key>:<secret>`; when that header is present it is used alone and the cookie is ignored (a bad header is 401, never a fallback), and token requests are exempt from CSRF (they carry no ambient credential a browser could attach). Public key (32 hex) and secret (64 hex); only the secret's SHA-256 digest is stored; the secret is shown once; tokens do not expire and can be revoked; a disabled user's tokens stop working. |
| Passwords | **Implemented (M3.1):** Argon2id (`argon2` 0.6) with m = 19456 KiB, t = 2, p = 1, random 16-byte salt, PHC string; verified with the parameters inside the string; 8 to 1024 bytes; hashing runs on the blocking thread pool. |
| Login lockout | **Implemented (M3.1):** per submitted username (also unknown ones), 5 consecutive failures, each within 15 minutes of the previous one (`last_failure_at`; an older failure restarts the count at 1), lock it for 15 minutes; counting is committed even when the login fails; concurrent attempts are serialized by a row lock. Unknown, disabled, wrong-password and locked all give one uniform error and spend one Argon2 verification (a dummy hash when there is no real one). |
| Deferred | OAuth/SSO, 2FA, password reset by email. |

JWT for first-party browser sessions is avoided (revocation complexity).

**Secrets rule.** No password, session token, CSRF token or API secret is stored in plaintext, and Forgebase itself never logs it or puts it in an error, `Debug` or `Display` output (PostgreSQL parameter logging is a known limit below). The only exceptions are the one-time return values of `login` and `create_api_token` and the one-time output of `forgebase token create`. Types that carry a secret implement `Debug` by hand and redact it; tests assert this.

**Known limits (M3.1).** The lockout can be used to lock a known user out (denial of service); `fb_login_failure` has one small row per failed username that is not cleaned up automatically (deferred: a later job can delete rows whose `last_failure_at` and `locked_until` are both NULL or older than 15 minutes); a caller that runs `login` inside its own transaction loses the failure counting if that transaction rolls back (call it on a pooled client); digests are compared by PostgreSQL, not in constant time (acceptable for 256-bit random values); there is no password complexity or breach check; Argon2 memory use (about 19 MiB per verification) and connection-pool exhaustion (parallel logins for one username each hold a pooled connection while they wait on the row lock) both need bounded login concurrency, which M3.3 provides (see "The HTTP layer" below); **PostgreSQL parameter logging:** plaintext session tokens, CSRF tokens and API secrets reach PostgreSQL as bind parameters (`sha256()` runs in SQL) and there is no TLS to PostgreSQL yet, so PostgreSQL can log them with `log_statement = all` or `log_min_duration_statement` - operators should set `log_parameter_max_length = 0` and `log_parameter_max_length_on_error = 0` and use a local or private network until TLS arrives.

## Authorization (implemented in M3.2, [ADR 0011](../adr/0011-permission-model-phase-1.md))

- **Phase 1 (M3.2):** role permissions per DocType (read, write, create, delete, submit, cancel, amend) plus an "owner only" condition (`if_owner`), declared as `[[permissions]]` in the DocType file. The built-in role `Administrator` and the trusted **system context** (`Caller::System`, used by the CLI and tests) bypass the rules. Access is the union over the caller's roles; there are no deny rules. **Deny by default:** a DocType without rules is closed to everyone else. **Child rows follow the parent's permissions** (a child DocType has no rules).
- **One evaluator.** `forgebase_core::permission::evaluate(&DocType, &Caller, Right) -> Access` (`All`, `OwnerOnly`, `Denied`) is pure and the only place a permission is decided; `forgebase-db` calls it in every operation (`insert`, `get`, `update`, `delete`, `submit`, `cancel`, `amend`, `list`), which all take a `Caller`. It is tested as a full matrix, and the integration tests (`forgebase-db/tests/permissions.rs`, `tests/list.rs`) cover every right with and without the role, `if_owner`, deny by default, the union of roles and the system context.
- **Information leakage (owner decision 9).** A document the caller cannot read behaves exactly like a missing one: `get` returns `None`, every other operation returns `NotFound` **before** the version is compared (a stale version is never a `Conflict` for a hidden document), and a Link to it is `LinkNotFound` (checked for new or changed Link values on `update` and `submit`; Links already stored on the document are kept, so they do not block the operation). A right that depends on no document (no read or write right on the DocType at all) is `PermissionDenied`, which names the DocType and the right, never a document. A readable document of somebody else under an `if_owner` write is `PermissionDenied` too. A "still linked" delete error names the referencing DocType only to a caller who can read it. Details and the order of the checks: [ADR 0011](../adr/0011-permission-model-phase-1.md).
- **Known limits (M3.2).** Unique constraints are global: a unique violation (a `unique` field, a naming field, an amended name) and `AlreadyAmended` can reveal that a document with that value exists even if the caller cannot read it. A "still linked" error still tells that some document links to the one being deleted. The system context is a bypass by design and must never be built from request data (M3.3 builds `Caller::User` only, from a validated session or token; the HTTP crate never names `Caller::System`). A caller's roles are read when the caller is built, so a role change applies from the next request.
- **Read-only database role (non-goal of M3.2; the open question is answered).** The Link lookup (`FOR KEY SHARE`) and the locking reads need the `UPDATE` privilege on the table, so a read-only database role cannot run the write operations or create documents with Link fields. M3.2 does not use such a role; reports (later) will run read-only queries that take no row locks, and a plain `list` takes none either.
- **Phase 2 (Proposed for M10, separate decision; sharing Later):** field-level permission levels, user permissions (record filters by linked value), sharing.
- Frappe's phase-2 matching rules are not fully verified (feature matrix, open questions 3-4); do not copy semantics until they are read from the official pages.

## The HTTP layer (implemented in M3.3)

Routes, statuses and the error envelope: [architecture, section 7](architecture.md#7-api-rest-resource-api-implemented-in-m33-the-rest-proposed). The security properties, in the order a request meets them:

- **Host validation first (owner decision 8).** The `Host` header (port ignored, case-insensitive) must be in `FORGEBASE_ALLOWED_HOSTS` (default `localhost,127.0.0.1`); a missing, repeated or unknown `Host` is `400 invalid_host`. An entry with a port can never match, so `forgebase serve` refuses it at startup (exit 1). It runs before routing, authentication, body parsing and the 404/405 answers, so it covers login too. This protects against Host-header poisoning and DNS rebinding for a single site; multi-site will resolve the site from the same list.
- **Authentication, uniform 401.** The `Authorization` header wins over the cookie. A missing, malformed, wrong, expired, revoked, idle or tampered credential, a disabled user and an unknown token all give the same `401 unauthenticated` body (a failed login has its own, equally uniform message). Authentication and CSRF are decided before the path, query or body of a request is looked at; an unauthenticated request with an oversized or malformed body is a 401.
- **CSRF (owner decision 5).** `X-Forgebase-CSRF` is checked against the session for every cookie-authenticated request that is not `GET`/`HEAD`. `GET` never changes state, except that a valid session is touched (`last_seen_at`).
- **No CORS (owner decision 8).** No `Access-Control-*` header is ever sent and `OPTIONS` is a 405, so browsers keep the same-origin policy. Front-ends are served from the same origin (a reverse proxy). Together with `SameSite=Lax`, the CSRF header and the JSON-only bodies (`Content-Type: application/json` is required, other types are 415) this closes cross-site request forgery; it is not a replacement for any of them.
- **The caller is a user.** The authenticated user becomes `Caller::User` with the roles read from the database for this request. `Caller::System` is never built in the HTTP crate; a test suite (`forgebase-http/tests/resources.rs`) runs the permission matrix over HTTP, and the document functions enforce every right.
- **Mapping errors do not describe closed DocTypes.** Before a body or `filters` is mapped (which names fields), the DocType-level right is checked with the same evaluator; a caller without it gets `403 permission_denied`, not a 422 that would list field names.
- **No leakage in responses (owner decision 9 survives the mapping).** An unreadable Link target gives the same `422 validation_failed` as a missing one; a delete blocked by documents of a DocType the caller cannot read does not name it; a hidden document is `404`, also for `PATCH` and `DELETE` and for a stale version. An unexpected error (database, pool, stored value) is logged to standard error and answered with `500 internal` and a generic message; a unique violation answers generically (the server text has the constraint and key). No response contains a password, session token, API secret or the database URL; the one-time `csrf_token` is only in the login response and the session token only in `Set-Cookie`.
- **Bounded work.** Request bodies are limited (default 1 MiB, `413 payload_too_large`); list `limit` has a hard maximum (500); concurrent logins are bounded by a semaphore (default 8, but at most half of the pool's maximum size and at least 1, so with a pool of 2 or more connections logins can never hold all of them; an excess login is `503 too_many_logins` with `Retry-After: 1`, never queued), which bounds Argon2 memory (about 19 MiB each) and the pooled connections that logins hold (the M3.1 known limits). A repeated query parameter, like an unknown one, is `400 invalid_query`, so the value cannot depend on which one a parser keeps. Every other request needs a pooled connection and waits for one without a timeout (deadpool default): a flood of authenticated requests can exhaust the pool.
- **Known limits (M3.3).** There is no TLS in the application (terminate it at a reverse proxy; the reverse proxy must also set or pass a correct `Host`, and `FORGEBASE_DEV_INSECURE_COOKIES=1` must not be used behind it); no rate limiting beyond the login bound and the per-username lockout (a proxy should limit by client address); no read timeout for slow clients (slowloris) in the application (a proxy should provide it); no request logging; the allowed hosts and DocType rules are read at startup (a change needs a restart); `Max-Age` of the cookie is fixed at the session's absolute lifetime (7 days) and the server decides validity (idle expiry 24 hours); `logout` does not accept an API token (revoke it with the CLI); errors raised by hyper before a request reaches the router (for example `431` for oversized headers, or a malformed HTTP request) bypass the error envelope and the `Cache-Control`/`nosniff` headers; the cookie name is fixed (owner decision 3), so the `__Host-` cookie prefix (which would bind the cookie to the exact host and `Path=/`) is a possible later hardening; there is no endpoint to create tokens or users over HTTP (use the CLI).

## Query enforcement (implemented in M3.2)

- All document reads go through a permission-filtered query path in `forgebase-db`. The read access of the caller is part of the SQL of the same statement (`AND "owner" = $n`, bound, for an `if_owner` read), also in the locking reads of update, delete, submit, cancel and amend; there is no "fetch then filter".
- **List query** (`forgebase_db::list`): a typed `ListQuery` (filters `=`, `!=`, `<`, `<=`, `>`, `>=`, `in`, `is null`, `like` on text fields only; multi-field sort, `name` always last; `limit` default 20, maximum 500, an error beyond it). Field names come from the metadata only (unknown ones are `InvalidQuery`), and every value is bound with a cast. A filter or a sort cannot reach a row the caller may not read, and neither can an offset past the caller's own rows.
- Custom endpoints (`/api/v1/method/{name}`) must declare the required permission explicitly (M3.3 and later; deferred by the owner). This contrasts with Frappe, where whitelisted methods do not check DocType permissions automatically (Source-indexed, see feature matrix).
- Pagination has a default limit and a hard maximum (implemented in `list`; exposed by the HTTP API as `limit` and `offset`).

## Injection defense

- SQL identifiers come only from validated metadata, are matched against a strict pattern and are always quoted.
- Values are always bound parameters. Generated DDL (schema sync) contains no values at all: only validated, quoted identifiers and numeric type parameters (`varchar(n)`, `numeric(p,s)`) taken from validated metadata; settings such as `lock_timeout` are passed as bound parameters.
- Identifiers are validated twice: by `forgebase-core` when metadata is loaded, and quoted by `forgebase_db::quote_ident` (doubling any `"`) at every use in generated SQL (implemented in M1.2).
- Document values and the actor are bound parameters, with an explicit cast per field type; a document write never interpolates a value into SQL. Document names are bound too (implemented in M1.3, tests store injection-like strings literally).
- Link fields (M2.1): the target `name` is a bound parameter of the lookup (`SELECT "id" FROM "doc_<target>" WHERE "name" = $1::text FOR KEY SHARE`) and the resolved `id` is bound as `uuid`; the target table name comes from validated metadata (`Link { target }` is checked as a DocType name when the definition is loaded) and is quoted. Generated DDL for Link fields (foreign keys, indexes) contains identifiers only. Tests store injection-like names literally. The foreign key (`ON DELETE RESTRICT`) is the integrity guarantee; the `FOR KEY SHARE` lock narrows the race between the lookup and the write. Conflicting versions (`expected_version`) are checked by the locking read that starts each `update` and `delete` (since M2.3), and again in the `WHERE` clause of the write.
- Child tables (M2.2): rows are written with one `INSERT` per row whose values are bound parameters with explicit casts (`$n::bigint`, ...), like the document itself; the child table name and column names come from validated metadata and are quoted; Link names inside rows are resolved by the same bound lookup. The parent id and the row position are bound too. The DDL for a child table (`parent_id` foreign key, indexes) contains identifiers only. Row values from the command-line tool go through the same validation as document values. Calling `forgebase-db` with a child DocType as the document type is refused (`DbError::ChildDocType`), so rows cannot be addressed without their parent; the rows follow the parent's permissions (M3.2): they are read and written with the parent document, under its rules, and the child DocType has no rules of its own.
- Naming series and docstatus (M2.4): the series prefix (rendered from the pattern and the database date) and the number are bound parameters of the `fb_series` statement; the pattern is validated when the DocType is loaded and the table name `fb_series` is fixed, so no document value reaches SQL text. The `docstatus` value written by submit and cancel is a constant of the `DocStatus` enum, not an input. Users cannot set `docstatus` or `amended_from`: they are not fields, so any value for them in a document or in changes is rejected as an unknown field, and both are reserved field names. A submitted document can only change `allow_on_submit` fields, also when a hook tries to change another (`DbError::FieldLocked`). Submit, cancel and amend have rights of their own (M3.2: the `submit`, `cancel` and `amend` rights of the permission model).
- Database connections do not use TLS yet (M1.2); connect over a local or private network until rustls support is added.
- List filters are a typed AST (M3.2, `forgebase_db::ListQuery`), never string-concatenated: field names are looked up in the metadata and quoted, every value is a bound parameter with a cast from the field type, `like` takes a bound pattern, and the owner condition of an `if_owner` read is a bound parameter too. Tests (`tests/list.rs`) try hostile field names, sort keys, DocType names and values.
- Reports (later) run with a read-only DB role.

## Multi-site isolation (when it arrives; Undecided)

Options, lean (database-per-site) and the day-one site/pool context constraint are in [architecture, section 9](architecture.md#9-multi-site-undecided). Security-relevant points: no cross-site queries; the site is resolved from the `Host` header against a configured list; a row-level tenant column is rejected because permission bugs would leak data.

## Secrets

Config file and environment variables only; never in DB metadata or logs. Session tokens and API secrets are stored hashed. Forgebase never logs them, but PostgreSQL may log bind parameters; see the known limits above.

## The command-line tool (M1.3)

`forgebase` is a **trusted local tool**: whoever can run it with a database URL has full access to that database, including creating users, setting passwords and creating API tokens (`forgebase user ...` and `forgebase token ...`, M3.1; passwords are read from standard input, never from an argument or environment variable, and `token create` is the only output of a secret). It has no authentication, and its `doc` commands run as the **system context** (`Caller::System`, M3.2), to which no permission rule applies; real users and their permissions apply to the HTTP API (M3.3). `--actor` names the system actor that is recorded in `owner` / `modified_by` on insert and update (on delete it is given to hooks and not stored); it is not verified and must not be treated as an identity. The database URL (with its password) is read from the `FORGEBASE_DATABASE_URL` environment variable, never from a command-line argument, and is not printed. Input is checked before any SQL runs (JSON mapping, then core validation), and a datetime whose UTC instant is outside the supported range is an error, not a panic.

## Audit

`owner`, `modified_by`, `modified_at` from day one. Full version history is deferred.

## Deferred items

OAuth/SSO, 2FA, field-level permissions, user permissions, sharing, full audit/version history, workflow-based edit restrictions, Postgres row-level security as defense in depth (idea only, not planned).

## Open questions for M3

Not decided; each needs an answer in the M3 plan:

- ~~Login rate limiting / brute-force protection.~~ Answered in M3.1 (ADR 0010): per-username lockout (5 failures, 15 minutes). Bounded login concurrency was added in M3.3 (semaphore, default 8, excess 503); throttling by client address is left to the reverse proxy (not built).
- ~~Session rotation: issue a new session token on login, and invalidate sessions on password change and logout.~~ Answered in M3.1 (ADR 0010): a new session on every login; password change and disabling delete all of the user's sessions; logout deletes the session.
- ~~CORS policy when cookies are used.~~ Answered in M3.3 (owner decision 8): no CORS at all; same-origin deployment behind a reverse proxy; no `Access-Control-*` header is sent (tested). The CORS middleware named in [ADR 0005](../adr/0005-http-stack.md) is not used.
- ~~`Host` header validation in single-site mode.~~ Answered in M3.3 (owner decision 8): validated against `FORGEBASE_ALLOWED_HOSTS` before everything else.
- ~~Argon2id parameters~~ Answered in M3.1 (ADR 0010): m = 19456 KiB, t = 2, p = 1 (see [dependency-evaluation, open question 9](dependency-evaluation.md#open-questions)).
- ~~Permission-aware Link name resolution.~~ Answered in M3.2 (owner decision 9, ADR 0011): a Link is resolved with the caller's read access on the target DocType, and a target the caller cannot read gives exactly the `LinkNotFound` of a missing one; `LinkedDocumentExists` names the referencing DocType only to a caller who can read it. Remaining, accepted limit: unique violations and `AlreadyAmended` can still reveal existence.
- ~~Read-only database role and `FOR KEY SHARE`.~~ Settled in M3.2 as a **non-goal**: Link lookups and locking reads need the `UPDATE` privilege on the table, so a read-only role cannot run the write operations; it is not used. Reports (later) must be designed around it.

## Required negative tests

Per the testing strategy in [maintenance-policy](maintenance-policy.md#testing-strategy), M3 is not complete without explicit negative tests. Status after M3.3: every item below that can exist today is implemented and tested against PostgreSQL; the multi-site item waits for multi-site, and custom endpoints (`/api/v1/method`) are not implemented (a request to them is a 404).

- every permission rule: a user without the role is denied (read, write, create, delete, submit, cancel, amend), and a DocType with no rules is denied to non-admins. *Tests:* `forgebase-db/tests/permissions.rs` (every right with and without its role, deny by default, union of roles); over HTTP `forgebase-http/tests/resources.rs` (`the_authorization_matrix_over_http`, `the_lifecycle_and_its_error_codes`);
- "owner only": another user's document is neither listed nor fetchable. *Tests:* `permissions.rs`, `list.rs`; over HTTP `if_owner_hides_the_documents_of_others` (404 for get, patch and delete, absent from the list, filters do not reveal it);
- list queries never return rows the user cannot read (including via filters, sorting and paging). *Tests:* `forgebase-db/tests/list.rs`; over HTTP the `if_owner` test above and `listing_filters_sorts_and_pages`;
- injection attempts in filters, field names, sort keys and DocType names are rejected or inert. *Tests:* `list.rs`; over HTTP `injection_attempts_are_inert` (hostile DocType path segments are 404, hostile filter and sort keys are 400, hostile values are inert);
- expired, revoked and tampered session tokens and wrong API secrets are rejected. *Tests:* `forgebase-db/tests/auth.rs`; over HTTP `forgebase-http/tests/auth.rs` (`expired_unknown_and_tampered_cookies_are_the_same_401`, `bad_tokens_are_the_same_401`, `a_disabled_user_loses_the_session`, `logout_ends_the_session_and_clears_the_cookie`, `lockout_works_over_http`, `a_failed_login_is_the_same_401_for_every_reason`);
- state-changing cookie-authenticated requests without a valid CSRF token are rejected. *Tests:* `a_cookie_session_reads_and_needs_csrf_to_change_things` (missing, wrong, another session's and malformed token; POST, PATCH and DELETE; the logout case is in `logout_ends_the_session_and_clears_the_cookie`), `an_api_token_needs_no_csrf`, `the_authorization_header_wins_over_the_cookie`;
- `Host` validation, no CORS, uniform errors (for every failure that reaches the router; hyper-level errors such as `431` or malformed HTTP bypass the envelope) and no leaked secrets. *Tests:* `the_host_is_checked_first_on_every_route`, `a_repeated_host_header_is_refused`, `configured_hosts_are_used_and_ipv6_works`, `no_cors_headers_anywhere`, `every_kind_of_failure_uses_the_envelope`, `the_body_limit_is_413_in_the_envelope`, `no_secret_appears_in_a_response_except_where_it_is_issued`, `internal_errors_are_generic`, `a_unique_violation_does_not_echo_the_key`, `concurrent_logins_are_bounded` (timing based) and, in `forgebase-http/src/lib.rs`, the deterministic `a_login_over_the_bound_is_503_without_touching_the_database` and `login_permits_never_take_every_connection`; decision 9 over HTTP: `decision_9_no_leaks_through_links`;
- custom endpoints without a declared permission are refused (`/api/v1/method` is not implemented, so the only behavior is the 404 of `every_kind_of_failure_uses_the_envelope`; the item applies again when custom endpoints exist);
- (when multi-site exists) a request for site A can never read site B data.
