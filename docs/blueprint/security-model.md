# Security model

Status: **Proposed** unless stated; of the sections below identifier and value handling in `forgebase-db` (M1.2, M1.3, M2.1, M2.2), the trust note for the command-line tool, the storage side of authentication (M3.1, [ADR 0010](../adr/0010-authentication-and-sessions.md), Accepted) the role permission model with its enforcement and the list query (M3.2, [ADR 0011](../adr/0011-permission-model-phase-1.md), Accepted) and the HTTP layer (M3.3: cookies, CSRF, Host validation, no CORS, the login concurrency bound, the error envelope) are implemented; the trust note for apps and app migrations (M5.1) is recorded below. Multi-site isolation is not. Architecture context: [architecture](architecture.md). Frappe behavior referenced is labelled in the [feature matrix](feature-matrix.md). Changes to authentication, authorization or multi-site isolation are high-impact: they need Stage 1 planning and independent Stage 3 review per [AGENTS.md](../../AGENTS.md).

## Principles

- **Deny by default everywhere.** A DocType with no permission rules is inaccessible except to the `Administrator` role and the trusted system context (implemented in M3.2).
- **One enforcement point.** A single permission evaluator in `forgebase-core` (`forgebase_core::permission::evaluate`); no endpoint bypasses it (implemented in M3.2: every document operation of `forgebase-db` calls it).
- **Framework owns the dangerous parts.** Identifiers, SQL, transactions and sessions are handled by the framework, not by app code.
- **Secrets stay out of the data plane** (see Secrets).

## Authentication (milestone M3; storage side implemented in M3.1, [ADR 0010](../adr/0010-authentication-and-sessions.md))

| Mechanism | Design |
|---|---|
| Browser sessions | Opaque random token (32 bytes from the operating system, 64 hex characters). **Implemented (M3.1):** only the SHA-256 digest is stored in `fb_session`, with a CSRF token digest, the user, an absolute expiry (7 days) and an idle expiry (24 hours since last use); every login creates a new session; logout, password change and disabling the user delete sessions. **Implemented (M3.3):** carried in the cookie `fb_session=<token>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=604800` (`Secure` is omitted only with the explicit `FORGEBASE_DEV_INSECURE_COOKIES=1` development mode, which prints a warning); every cookie-authenticated request that is not `GET`/`HEAD` needs the session's CSRF token in the `X-Forgebase-CSRF` header (`check_csrf`, else 403 `csrf_failed`; the token is returned once by the login response). Logout (CSRF required) deletes the session and clears the cookie. |
| API tokens (machine clients) | **Implemented (M3.1; HTTP in M3.3):** sent as `Authorization: token <key>:<secret>`; when that header is present it is used alone and the cookie is ignored (a bad header is 401, never a fallback), and token requests are exempt from CSRF (they carry no ambient credential a browser could attach). Public key (32 hex) and secret (64 hex); only the secret's SHA-256 digest is stored; the secret is shown once; tokens do not expire and can be revoked; a disabled user's tokens stop working. |
| Passwords | **Implemented (M3.1):** Argon2id (`argon2` 0.6) with m = 19456 KiB, t = 2, p = 1, random 16-byte salt, PHC string; verified with the parameters inside the string; 8 to 1024 bytes; hashing runs on the blocking thread pool. |
| Login lockout | **Implemented (M3.1):** per submitted username (also unknown ones), 5 consecutive failures, each within 15 minutes of the previous one (`last_failure_at`; an older failure restarts the count at 1), lock it for 15 minutes; counting is committed even when the login fails; concurrent attempts are serialized by a row lock. Unknown, disabled, wrong-password and locked all give one uniform error and spend one Argon2 verification (a dummy hash when there is no real one). |
| Deferred | OAuth/SSO, 2FA, password reset by email. |

JWT for first-party browser sessions is avoided (revocation complexity).

**Secrets rule.** No password, session token, CSRF token or API secret is stored in plaintext, and Forgebase itself never logs it or puts it in an error, `Debug` or `Display` output (PostgreSQL parameter logging is a known limit below). The only exceptions are the one-time return values of `login` and `create_api_token` and the one-time output of `forgebase token create`. Types that carry a secret implement `Debug` by hand and redact it; tests assert this.

**Known limits (M3.1).** The lockout can be used to lock a known user out (denial of service); `fb_login_failure` has one small row per failed username; since M6.2 the built-in job `forgebase.purge_login_failures` deletes the rows that no longer count or lock (see "Background jobs" below), so for an attacker who tries many usernames, each row lives at most about 15 minutes after its last failure plus the 60 minute purge interval, while a worker runs; a caller that runs `login` inside its own transaction loses the failure counting if that transaction rolls back (call it on a pooled client); digests are compared by PostgreSQL, not in constant time (acceptable for 256-bit random values); there is no password complexity or breach check; Argon2 memory use (about 19 MiB per verification) and connection-pool exhaustion (parallel logins for one username each hold a pooled connection while they wait on the row lock) both need bounded login concurrency, which M3.3 provides (see "The HTTP layer" below); **PostgreSQL parameter logging:** plaintext session tokens, CSRF tokens and API secrets reach PostgreSQL as bind parameters (`sha256()` runs in SQL) so PostgreSQL can log them with `log_statement = all` or `log_min_duration_statement` - operators should set `log_parameter_max_length = 0` and `log_parameter_max_length_on_error = 0`, and use a private network or `sslmode=require` in the database URL (TLS to PostgreSQL exists since M9.0, [ADR 0018](../adr/0018-postgres-tls.md); it is off unless the URL asks for it).

## Background jobs (M6.1, [ADR 0013](../adr/0013-jobs-scheduler-and-transactional-outbox.md))

- **Jobs run as the trusted system context** (`Caller::System`, no permission rules) with an attributed actor, `job:<app>.<job>`, recorded as `owner` / `modified_by` of what a job writes and given to hooks. A job is app code compiled into the binary and is trusted like a hook; it is not a way to act as a user. Jobs that a job or a hook enqueues are attributed to the caller, or to `job:<app>.<job>`; a job enqueued with the CLI to `--actor` (default `cli`).
- **Payloads and errors are stored in clear text** in `fb_job.payload` and `fb_job.last_error`, and `forgebase job show` prints them. Never put a secret (a password, a token, a key) in a payload or an error message: pass the id of a document and read it in the job.
- **The CLI is a trusted local tool.** `job list|show|retry|enqueue` and `worker` read the database URL from the environment and do not authenticate anyone, like the other commands. There is **no HTTP or desk interface for jobs**, so no remote caller can enqueue, list or retry a job except through what an app's own hooks enqueue on a request that the caller was allowed to make. An unknown job name from a hook is refused and answered as an internal error (a mistake of the app, not of the caller).
- **Clean-up of login failures and sessions (M6.2, ADR 0013).** The built-in jobs `forgebase.purge_login_failures` and `forgebase.purge_sessions` run every 60 minutes in every binary that has a running worker. `purge_login_failures` deletes only rows that cannot change a login: not locked now and the last failure older than the failure window (15 minutes), using the constants and the condition of `login`; a locked username or one with a counting failure keeps its row, so the lockout is not weakened. `purge_sessions` deletes the sessions `validate_session` already refuses (past the 7 day expiry or idle for 24 hours), so no valid session is ended. `purge_jobs` deletes `done` and `dead` jobs 7 days after they finished (a retried dead job is queued again and is not touched; owner decision 2026-10-30). Expired sessions and stale failure rows are harmless without a worker (they are refused or ignored when used) but accumulate: run a worker. The jobs run as the system context in the worker's transaction, like any job.
- **Schedules** are stored in `fb_schedule` by `forgebase migrate` from what the binary declares; a worker never writes a definition, and there is no HTTP interface for them. Whoever can run `migrate` can change what runs and when, as with app migrations.
- **Limits.** The payload is at most 64 KiB of JSON. A worker claims only job names its binary knows; a job of an unknown name is left alone. Delivery is at-least-once: a handler can run again after a crash, so external effects must be safe to repeat.

## Authorization (implemented in M3.2, [ADR 0011](../adr/0011-permission-model-phase-1.md))

- **Phase 1 (M3.2):** role permissions per DocType (read, write, create, delete, submit, cancel, amend, and since M9.3 export and import) plus an "owner only" condition (`if_owner`), declared as `[[permissions]]` in the DocType file. The built-in role `Administrator` and the trusted **system context** (`Caller::System`, used by the CLI and tests) bypass the rules. Access is the union over the caller's roles; there are no deny rules. **Deny by default:** a DocType without rules is closed to everyone else. **Child rows follow the parent's permissions** (a child DocType has no rules).
- **One evaluator.** `forgebase_core::permission::evaluate(&DocType, &Caller, Right) -> Access` (`All`, `OwnerOnly`, `Denied`) is pure and the only place a permission is decided; `forgebase-db` calls it in every operation (`insert`, `get`, `update`, `delete`, `submit`, `cancel`, `amend`, `list`), which all take a `Caller`. It is tested as a full matrix, and the integration tests (`forgebase-db/tests/permissions.rs`, `tests/list.rs`) cover every right with and without the role, `if_owner`, deny by default, the union of roles and the system context.
- **Information leakage (owner decision 9).** A document the caller cannot read behaves exactly like a missing one: `get` returns `None`, every other operation returns `NotFound` **before** the version is compared (a stale version is never a `Conflict` for a hidden document), and a Link to it is `LinkNotFound` (checked for new or changed Link values on `update` and `submit`; Links already stored on the document are kept, so they do not block the operation). A right that depends on no document (no read or write right on the DocType at all) is `PermissionDenied`, which names the DocType and the right, never a document. A readable document of somebody else under an `if_owner` write is `PermissionDenied` too. A "still linked" delete error names the referencing DocType only to a caller who can read it. Details and the order of the checks: [ADR 0011](../adr/0011-permission-model-phase-1.md).
- **Known limits (M3.2).** Unique constraints are global: a unique violation (a `unique` field, a naming field, an amended name) and `AlreadyAmended` can reveal that a document with that value exists even if the caller cannot read it. A "still linked" error still tells that some document links to the one being deleted. The system context is a bypass by design and must never be built from request data (M3.3 builds `Caller::User` only, from a validated session or token; the HTTP crate never names `Caller::System`). A caller's roles are read when the caller is built, so a role change applies from the next request.
- **Read-only database role (non-goal of M3.2; the open question is answered).** The Link lookup (`FOR KEY SHARE`) and the locking reads need the `UPDATE` privilege on the table, so a read-only database role cannot run the write operations or create documents with Link fields. M3.2 does not use such a role; reports (M8.4, below) run in a `READ ONLY` transaction instead, which takes no row locks, and a plain `list` takes none either.
- **Workflow transitions (M8.1, [ADR 0015](../adr/0015-workflow-states-and-transitions.md)).** A transition needs one of the roles the transition names **and** the right its docstatus move needs (write for draft to draft and submitted to submitted, submit for draft to submitted, cancel for submitted to cancelled). The right is decided by `evaluate` and by nothing else; `forgebase_core::permission::transition_access` only adds the role, so a role in a workflow can never grant a right the DocType's `[[permissions]]` deny, and the right without the role is refused too. `if_owner` applies to the document exactly as for update, submit and cancel; `Administrator` and the system context pass both checks. The document is locked with the read grant first, so a hidden document is `NotFound` (before the version is compared) and an unknown action on a readable one is `UnknownTransition`. On a DocType with a workflow plain submit and cancel are refused (`WorkflowRequired`, before anything else is looked up, so it says nothing about a document), so no state change escapes the check, and a plain update of a draft in a state with `edit_roles` needs one of those roles. `workflow_state` is not a field: no caller can set it. The workflow roles and `edit_roles` are **never sent** by the metadata API (like `[[permissions]]`); `GET .../transitions` answers what the calling user may do, computed by the same function. `forgebase doc transition` is the system context like every `doc` command: the roles are **not** checked there. The transition log (`fb_workflow_log`) records the actor and is deleted with its document; it is a history for users, not an audit trail. Tests: `forgebase-db/tests/workflow.rs` (role without right, right without role, `if_owner`, Administrator and system, hidden document, stale version before action, concurrency, atomicity), `forgebase-http/tests/workflow.rs`, `forgebase-core` unit tests of `transition_access`.
- **Saved list views and the group-by summary (M8.3, [architecture, section 11](architecture.md#11-desk-reports-workflow)).** *Views are private.* A private view (`fb_saved_view.owner_id` set) is listed to its owner only, and for anyone else it does not exist: `PATCH` and `DELETE` answer 404 `not_found`, with the message of a missing view and **before** the version is compared, an Administrator included, so nothing tells that it exists. A shared view (`owner_id` null) is created, changed and deleted by an Administrator (or the system context) only; a non-administrator who tries gets 403, because they can see it. Both need the **read right on the DocType**, decided by the one evaluator (`access_to`, the same call as `list`), so a user who cannot read a DocType cannot list, create or change its views. A view carries filters, a sort and columns, never a right: opening it runs the ordinary list query under the caller's own read scope, and an Administrator chooses what a shared view's filters contain; they are visible to every reader of the DocType. A view is validated when written (labels, size 16 KiB, at most 100 private views per user and DocType and 100 shared per DocType, the filters and sort by the list's own validation) and not when read; a stale view fails in the list with `400 invalid_query`, never in SQL. *The summary adds no right.* `forgebase-db::summary` takes the read scope (`read_owner`, so an `if_owner` read counts only the caller's own documents, and no read right is 403) and the filters (`conditions`) from the code `list` uses; it has no permission check of its own. Group-by and aggregate fields come from the DocType metadata only (quoted identifiers, bound values), a child DocType is refused, at most 500 groups and 6 aggregates are returned, and a filter on a field the caller cannot see the rows of cannot reveal them, as in a list. Tests: `forgebase-db/tests/views.rs` (privacy, shared rule, the read right, validation, labels, limits, versions, cascade with the user), `forgebase-db/tests/summary.rs` (`if_owner`, deny, filters, validation, truncation), `forgebase-http/tests/views.rs` (status codes, 401, CSRF, the 404, envelopes).
- **Phase 2 (Proposed for M10, separate decision; sharing Later):** field-level permission levels, user permissions (record filters by linked value), sharing.
- Frappe's phase-2 matching rules are not fully verified (feature matrix, open questions 3-4); do not copy semantics until they are read from the official pages.

## Apps and app migrations (M5.1, [ADR 0012](../adr/0012-app-model-and-public-api-boundary.md))

An app is **trusted code compiled into the binary** ([ADR 0006](../adr/0006-extension-model.md)); there is no sandbox between an app and the framework, and none is planned. Consequences:

- **App migrations are SQL that runs with the database role of the binary**, the same role as the framework migrations and the schema sync, so an app migration can change or read any table, including `fb_user` and the sessions. This is by design: whoever can build the binary can already run any code with that role. Review the SQL of an app like any code you ship. They are checksummed, so an applied migration that is edited later is refused, but that is integrity of the history, not a security boundary.
- **Apps cannot reach another app's definitions** through the API: a DocType belongs to one app and no app can change it; an app may link to and hook only DocTypes of the apps it depends on (checked at startup). Hooks have no database access ([ADR 0009](../adr/0009-lifecycle-pipeline-and-hooks.md)) and run after the permission checks, so a hook of an extending app sees only operations that were allowed.
- **The system context and the public API.** `Caller::System` is not re-exported by the `forgebase` crate: an app has no API to run document operations as the system context. (The `forgebase` command-line tool uses it, as before.)
- **The `testing` feature** creates and drops databases on the server of `FORGEBASE_TEST_DATABASE_URL` and sets a fixed, public password for its test users; it is off by default and meant for `[dev-dependencies]` only.

## The HTTP layer (implemented in M3.3)

Routes, statuses and the error envelope: [architecture, section 7](architecture.md#7-api-rest-resource-api-implemented-in-m33-metadata-and-session-routes-in-m41-the-rest-proposed). The security properties, in the order a request meets them:

- **Host validation first (owner decision 8).** The `Host` header (port ignored, case-insensitive) must be in `FORGEBASE_ALLOWED_HOSTS` (default `localhost,127.0.0.1`); a missing, repeated or unknown `Host` is `400 invalid_host`. An entry with a port can never match, so `forgebase serve` refuses it at startup (exit 1). It runs before routing, authentication, body parsing and the 404/405 answers, so it covers login too. This protects against Host-header poisoning and DNS rebinding. With a config file (M7.1) the `Host` selects the site instead; see [multi-site isolation](#multi-site-isolation-m71-accepted-adr-0014).
- **Authentication, uniform 401.** The `Authorization` header wins over the cookie. A missing, malformed, wrong, expired, revoked, idle or tampered credential, a disabled user and an unknown token all give the same `401 unauthenticated` body (a failed login has its own, equally uniform message). Authentication and CSRF are decided before the path, query or body of a request is looked at; an unauthenticated request with an oversized or malformed body is a 401.
- **CSRF (owner decision 5).** `X-Forgebase-CSRF` is checked against the session for every cookie-authenticated request that is not `GET`/`HEAD`; the header must be present exactly once (a repeated header is refused like a missing one, so the outcome never depends on which value a parser keeps; same for the refresh header of `GET /api/v1/session`, M4.2). `GET` never changes state, except that a valid session is touched (`last_seen_at`) and that `GET /api/v1/session` rotates the CSRF token (next bullet).
- **CSRF token rotation (M4.1).** The desk keeps the CSRF token in memory only (never in `localStorage`, `sessionStorage`, IndexedDB or a script-readable cookie). To recover it after a page reload, `GET /api/v1/session` validates the cookie session (same rules as `validate_session`) and **replaces** the stored CSRF digest with the digest of a new random token, returned once in the body with `Cache-Control: no-store`; only the digest is stored. This does not weaken CSRF protection: a cross-site page cannot read the response (no CORS headers, tested) and the cookie is `SameSite=Lax`; anyone who holds the session cookie could log in anyway. **The refresh header.** Because a cookie-credentialed `GET` (a top-level navigation or an `<img>` of another site) would otherwise rotate the token and so make the desk's in-memory token stop working (a nuisance-level denial of service), the route requires the request header `X-Forgebase-CSRF: refresh`; without it the answer is `400 bad_request` and nothing is rotated. A navigation or `<img>` cannot send a non-safelisted header, and a cross-origin `fetch` with it needs a preflight, which gets 405 with no CORS headers. Tests: `the_session_route_needs_the_refresh_header_and_does_not_rotate_without_it`. Cost: the token held by another tab of the same session stops working; the desk handles `403 csrf_failed` by calling `/api/v1/session` once and retrying the request once. An API token has no session: 400.
- **Static desk serving and CSP (M4.1).** `forgebase serve` serves the built desk only when `FORGEBASE_DESK_DIR` is set, after the Host check. Only `index.html` and files directly in `assets/` with a name matching `^[A-Za-z0-9][A-Za-z0-9._-]*$` and a known extension are served; the name is checked on the raw path without percent-decoding, so `..`, `%2e%2e`, `%2f`, `%5c`, NUL, absolute paths and sub-directories are all 404 without a file system access (tests: `forgebase-http/tests/desk.rs`). Desk responses carry `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; font-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin` and `nosniff`; `index.html` is `no-store`, hashed assets are `immutable`. The desk has no inline script or style, no `dangerouslySetInnerHTML` and no `style` props (ESLint rules); every value is rendered as text by React. Known limit: the directory is trusted (symbolic links in it are followed); it is the operator's build output.
- **The desk hides, the API enforces (M4.2).** The form view shows a button or an editable control only when the metadata `rights`, the document's docstatus and `allow_on_submit` allow it (Submit, Cancel, Amend and Delete are hidden, not disabled, when the user lacks the right; a submitted document is editable only in its `allow_on_submit` fields; for an `"own"` right the desk acts only on documents the user owns). This is a convenience: every one of those operations is refused by the API for a user without the right (the authorization tests of M3 and one refused request in the Playwright smoke test), and the desk never relies on its own checks. The smoke test also asserts that `localStorage`, `sessionStorage` and `document.cookie` are empty and the session cookie is `HttpOnly`. **Known limit:** a document whose name is `.` or `..` cannot be addressed through `/api/v1/resource/<doctype>/<name>` (the browser resolves the dot segment before sending); the desk says so instead of requesting another URL.
- **`read_only` fields are enforced on the server (UX.1).** A field marked `read_only` in the DocType file is written only by hooks and migrations: `forgebase-db` refuses a caller's value for it (insert, update and the rows of tables, also for the CLI and a job's documents handle) before any hook runs, so a client cannot forge a computed value such as a total; the desk merely does not send such fields. See the [file format](architecture.md#doctype-file-format).
- **Metadata is permission-filtered (M4.1).** `GET /api/v1/meta` lists only DocTypes the caller can read and `GET /api/v1/meta/{doctype}` is 403 for one they cannot, using the same evaluator; neither contains documents, role names or `[[permissions]]` rules. The `rights` the desk uses to hide buttons are advisory: the API enforces every right again.
- **Link titles follow the caller's read rules (UX.4, owner decision U7).** `?link_titles=1` adds the `title_field` values of the documents that Link values point to. `forgebase_db::link_titles` applies the caller's read scope exactly as `list` does (the one evaluator of `forgebase-core`; an `if_owner` read limits the query to the caller's own documents in SQL, and there is no second permission check): a target the caller cannot read gets **no entry**, so the desk shows the plain name as before, and a title never reveals a document that a read would not return. One query per target DocType, bound parameters only, at most 500 names per target. Any value of the parameter other than `1` is `400 invalid_query`; without it the response is unchanged. Tests: `forgebase-db/tests/link_titles.rs` (readable, `if_owner` of somebody else, no right, no `title_field`, child rows, a page of 50) and `forgebase-http/tests/link_titles.rs`.
- **The command bar has no storage (UX.4, owner decision U5).** It works only on what the desk already holds (the DocTypes of `GET /api/v1/meta`, which are permission-filtered, and the last ten documents opened in the tab, **in memory**); it asks the server for nothing, searches no document content and writes nothing to browser storage (the ESLint rule that forbids it still applies, and the smoke test asserts empty storage after using it). The self-hosted font is served from `'self'` like every other asset, so the Content-Security-Policy (`font-src 'self'`) is unchanged and the page makes no request to a font provider.
- **No CORS (owner decision 8).** No `Access-Control-*` header is ever sent and `OPTIONS` is a 405, so browsers keep the same-origin policy. Front-ends are served from the same origin (a reverse proxy). Together with `SameSite=Lax`, the CSRF header and the JSON-only bodies (`Content-Type: application/json` is required, other types are 415) this closes cross-site request forgery; it is not a replacement for any of them.
- **The caller is a user.** The authenticated user becomes `Caller::User` with the roles read from the database for this request. `Caller::System` is never built in the HTTP crate; a test suite (`forgebase-http/tests/resources.rs`) runs the permission matrix over HTTP, and the document functions enforce every right.
- **Mapping errors do not describe closed DocTypes.** Before a body or `filters` is mapped (which names fields), the DocType-level right is checked with the same evaluator; a caller without it gets `403 permission_denied`, not a 422 that would list field names.
- **No leakage in responses (owner decision 9 survives the mapping).** An unreadable Link target gives the same `422 validation_failed` as a missing one; a delete blocked by documents of a DocType the caller cannot read does not name it; a hidden document is `404`, also for `PATCH` and `DELETE` and for a stale version. An unexpected error (database, pool, stored value) is logged to standard error and answered with `500 internal` and a generic message; a unique violation answers generically (the server text has the constraint and key). No response contains a password, session token, API secret or the database URL; the one-time `csrf_token` is only in the login response and the session token only in `Set-Cookie`.
- **Bounded work.** Request bodies are limited (default 1 MiB, `413 payload_too_large`); list `limit` has a hard maximum (500); concurrent logins are bounded by a semaphore (default 8, but at most half of the pool's maximum size and at least 1, so with a pool of 2 or more connections logins can never hold all of them; an excess login is `503 too_many_logins` with `Retry-After: 1`, never queued), which bounds Argon2 memory (about 19 MiB each) and the pooled connections that logins hold (the M3.1 known limits). A repeated query parameter, like an unknown one, is `400 invalid_query`, so the value cannot depend on which one a parser keeps. Every other request needs a pooled connection and waits for one without a timeout (deadpool default): a flood of authenticated requests can exhaust the pool.
- **Known limits (M3.3).** There is no TLS in the application (terminate it at a reverse proxy; the reverse proxy must also set or pass a correct `Host`, and `FORGEBASE_DEV_INSECURE_COOKIES=1` must not be used behind it); no rate limiting beyond the login bound and the per-username lockout (a proxy should limit by client address); no read timeout for slow clients (slowloris) in the application (a proxy should provide it); no request logging; the allowed hosts and DocType rules are read at startup (a change needs a restart); `Max-Age` of the cookie is fixed at the session's absolute lifetime (7 days) and the server decides validity (idle expiry 24 hours); `logout` does not accept an API token (revoke it with the CLI); errors raised by hyper before a request reaches the router (for example `431` for oversized headers, or a malformed HTTP request) bypass the error envelope and the `Cache-Control`/`nosniff` headers; the cookie name is fixed (owner decision 3), so the `__Host-` cookie prefix (which would bind the cookie to the exact host and `Path=/`) is a possible later hardening; there is no endpoint to create tokens or users over HTTP (use the CLI).

## Query enforcement (implemented in M3.2)

- All document reads go through a permission-filtered query path in `forgebase-db`. The read access of the caller is part of the SQL of the same statement (`AND "owner" = $n`, bound, for an `if_owner` read), also in the locking reads of update, delete, submit, cancel and amend; there is no "fetch then filter".
- **List query** (`forgebase_db::list`): a typed `ListQuery` (filters `=`, `!=`, `<`, `<=`, `>`, `>=`, `in`, `is null`, `like` on text fields only; multi-field sort, `name` always last; `limit` default 20, maximum 500, an error beyond it). Field names come from the metadata only (unknown ones are `InvalidQuery`), and every value is bound with a cast. A filter or a sort cannot reach a row the caller may not read, and neither can an offset past the caller's own rows.
- Custom endpoints (`/api/v1/method/{app}.{method}`, M9.1) must declare who may call them explicitly (`.roles(..)` or `.any_user()`, else a startup error), run as the caller and are covered by [App methods](#app-methods-m91-adr-0019) below. This contrasts with Frappe, where whitelisted methods do not check DocType permissions automatically (Source-indexed, see feature matrix).
- Pagination has a default limit and a hard maximum (implemented in `list`; exposed by the HTTP API as `limit` and `offset`).

## Injection defense

- SQL identifiers come only from validated metadata, are matched against a strict pattern and are always quoted.
- Values are always bound parameters. Generated DDL (schema sync) contains no values at all: only validated, quoted identifiers and numeric type parameters (`varchar(n)`, `numeric(p,s)`) taken from validated metadata; settings such as `lock_timeout` are passed as bound parameters.
- Identifiers are validated twice: by `forgebase-core` when metadata is loaded, and quoted by `forgebase_db::quote_ident` (doubling any `"`) at every use in generated SQL (implemented in M1.2).
- Document values and the actor are bound parameters, with an explicit cast per field type; a document write never interpolates a value into SQL. Document names are bound too (implemented in M1.3, tests store injection-like strings literally).
- Link fields (M2.1): the target `name` is a bound parameter of the lookup (`SELECT "id" FROM "doc_<target>" WHERE "name" = $1::text FOR KEY SHARE`) and the resolved `id` is bound as `uuid`; the target table name comes from validated metadata (`Link { target }` is checked as a DocType name when the definition is loaded) and is quoted. Generated DDL for Link fields (foreign keys, indexes) contains identifiers only. Tests store injection-like names literally. The foreign key (`ON DELETE RESTRICT`) is the integrity guarantee; the `FOR KEY SHARE` lock narrows the race between the lookup and the write. Conflicting versions (`expected_version`) are checked by the locking read that starts each `update` and `delete` (since M2.3), and again in the `WHERE` clause of the write.
- Child tables (M2.2): rows are written with one `INSERT` per row whose values are bound parameters with explicit casts (`$n::bigint`, ...), like the document itself; the child table name and column names come from validated metadata and are quoted; Link names inside rows are resolved by the same bound lookup. The parent id and the row position are bound too. The DDL for a child table (`parent_id` foreign key, indexes) contains identifiers only. Row values from the command-line tool go through the same validation as document values. Calling `forgebase-db` with a child DocType as the document type is refused (`DbError::ChildDocType`), so rows cannot be addressed without their parent; the rows follow the parent's permissions (M3.2): they are read and written with the parent document, under its rules, and the child DocType has no rules of its own.
- Naming series and docstatus (M2.4): the series prefix (rendered from the pattern and the database date) and the number are bound parameters of the `fb_series` statement; the pattern is validated when the DocType is loaded and the table name `fb_series` is fixed, so no document value reaches SQL text. The `docstatus` value written by submit and cancel is a constant of the `DocStatus` enum, not an input. Users cannot set `docstatus` or `amended_from`: they are not fields, so any value for them in a document or in changes is rejected as an unknown field, and both are reserved field names. A submitted document can only change `allow_on_submit` fields, also when a hook tries to change another (`DbError::FieldLocked`). Submit, cancel and amend have rights of their own (M3.2: the `submit`, `cancel` and `amend` rights of the permission model).
- Database connections use TLS when the URL says `sslmode=require` (or `verify-ca`, `verify-full`): always with full verification (chain and host name), against the operating system's roots or only the `sslrootcert` file; without `sslmode` or with `disable` there is no TLS, and `prefer` is refused so that a failure never turns into a silent downgrade (M9.0, [ADR 0018](../adr/0018-postgres-tls.md)). The default is no TLS, so on a network that is not private the operator must set `sslmode=require`. `site backup` and `site restore` pass the same choice to `pg_dump` and `pg_restore` (`PGSSLMODE=verify-full`). **The operating system's trust store is whatever the host or image provides**, and every certificate in it is a trusted root, so what it holds is part of the trust decision. On Linux `rustls-native-certs` reads `SSL_CERT_FILE` (only that file, when set) and `SSL_CERT_DIR`, and otherwise the default locations (a bundle file or the directory `/etc/ssl/certs`); a stray certificate file there is trusted, and rustls does not check `CA:FALSE` on a trust anchor. The Docker image therefore sets `SSL_CERT_FILE` to its one CA bundle and removes the base image's public `ssl-cert-snakeoil` test certificate and key (its private key is in every copy of the public image: anybody could sign a certificate that a client reading the whole directory would accept). `SSL_CERT_FILE` limits rustls only; libpq (`pg_dump`, `pg_restore`) also reads the hashed files of `/etc/ssl/certs`, so the image keeps that directory empty apart from the bundle. CI checks that. Outside Docker, keep the trust store clean, or use `sslrootcert=<path>` to trust one CA only. The URL is parsed where `tokio-postgres` parses it; a raw `/`, `?` or `#` before the first `@` is refused (percent-encode special characters in the user name and password, see [ADR 0018](../adr/0018-postgres-tls.md)), and a URL whose TLS choice the two parsers read differently is refused.
- List filters are a typed AST (M3.2, `forgebase_db::ListQuery`), never string-concatenated: field names are looked up in the metadata and quoted, every value is a bound parameter with a cast from the field type, `like` takes a bound pattern, and the owner condition of an `if_owner` read is a bound parameter too. Tests (`tests/list.rs`) try hostile field names, sort keys, DocType names and values.
- Query reports (M8.4): the parameters are typed and always bound, the statement runs in a `READ ONLY` transaction with a timeout and a row limit, and the SQL is the app's own compiled-in code; see [Query reports](#query-reports-m84-adr-0016). There is no read-only database role (see the *Read-only database role* paragraph).

## Query reports (M8.4, ADR 0016)

[ADR 0016](../adr/0016-query-reports-read-only-execution.md). *Row-level rules do not apply inside a report.* A report is SQL that the app compiled into the binary (trusted code, like an app migration); it shows what it selects to **every role that may run it**, whatever the DocType `[[permissions]]` say, `if_owner` included. Access is **by role only**: a report names at least one role (an empty list is a startup error, so there is no "any user" report and deny by default holds), the Administrator role and the system context always pass, and anyone else gets **404**, the same answer as for a report that does not exist, **before the request body is mapped** (so no parameter name is revealed) and the report is not in `GET /api/v1/report`. The decision is `forgebase_core::permission::can_run_report`, next to `evaluate`, and `forgebase-db` checks it again. *Protections:* the statement runs in a **`READ ONLY` transaction** (a write fails with SQLSTATE 25006 and changes nothing), with a **statement timeout** (30 s by default, at most 300 s per report) and a **lock timeout** (5 s), and returns **at most `max_rows` rows** (10 000 by default, at most 100 000; the server stops after `max_rows + 1`); parameters are **typed, checked like fields and always bound**, never interpolated (a hostile value is data: tested with `'); DROP TABLE ...; --`); the **SQL text is never sent**: not in the list, not in an error, not in the response of a failing report (a write attempt or a mismatch is a generic 500 that names the report in the server log only). A report cannot run a statement that is not a query: the prepared statement's parameter and column counts are compared with the declaration before it runs, and `forgebase migrate` prepares every report and refuses a mismatch. *What a report can still do:* read any table the database role of the binary can read, in the time and row limits, and take session-level state such as an advisory lock (`pg_advisory_lock`) or a prepared statement for the length of its own request (M9.1: a report runs on a connection that is **closed afterwards instead of being returned to the pool**, so nothing it sets, locks or prepares reaches another request, see the [amendment of ADR 0016](../adr/0016-query-reports-read-only-execution.md#amendment-2026-10-31-m91-a-reports-connection-is-not-pooled-again); the test holds a pool of one connection and checks the lock is gone on the next checkout); the read-only transaction is a guard against mistakes, **not** a sandbox against malicious SQL, which is why the SQL must be reviewed like any code. *Guidance for app authors:* **the caller is not available to the SQL in M8** (no `$caller` parameter), so a report cannot filter by the signed-in user; give it only to roles that may see all the rows it selects, and keep the amount of detail in a report in line with its roles. A Link parameter is only bound (no existence check, no read rule). The titles of Link columns (`?link_titles=1`) follow the caller's read rules, so a title never shows a document the caller could not read, but the **names** in the Link column are what the SQL returned. Run time and row limits bound the cost of a request, not the cost of many requests: a role that may run a slow report may run it repeatedly (there is no rate limit on reports; the pool is shared with the rest of the API).

## App methods (M9.1, ADR 0019)

[ADR 0019](../adr/0019-app-method-endpoints.md). *Who may call.* A method declares **exactly one** of `.roles(&[..])` (non-empty) or `.any_user()`; neither, an empty list or both is a startup error, so a method cannot be open by omission and **there are no guest methods** (every call is authenticated: a session cookie, with the CSRF header on the `POST`, or an API token, which needs none). `forgebase_core::permission::can_call_method` is the whole gate; the Administrator role passes `.roles`. A method that does not exist, whose app the site does not install, or that the caller may not call is the same `404 not_found` with the same body, so method names cannot be probed; only authentication, CSRF and the shape of the body (JSON, an object, within the body limit) are decided before it, and none of them depends on the method. *With whose rights.* The handler's `documents()` handle is a `Caller::User` built from the request, and the context offers no way to the system context: every call goes through the same `forgebase-db` functions as the document API, so the evaluator of ADR 0011 (`if_owner`, read rules, read-only fields, `edit_roles`, workflow roles) is the only decision and a method can do no more than its caller could do by hand. A method that needs more is a job, which is enqueued visibly and runs as the system. A role that may call a method is **not** thereby allowed to read what the method reads, and the method's own result is what the caller sees: an app author decides what a method returns (for example a total over documents the caller cannot read would reveal them), so a method that aggregates should read through the handle (the caller's read scope applies) or be restricted to roles that may see everything. *Transactions.* One transaction per call; `Ok` commits and every error rolls everything back, including enqueued jobs (the outbox) and a panic (the handler runs on its own task, the connection is closed and not pooled with an open transaction, the client gets a generic 500). *Errors.* The app's message of a `method_error` (400 or 422) is sent as written, so an app must not put internals in it; every other error goes through the one mapping of `forgebase-http` (`From<DbError> for ApiError`), which keeps SQL, constraint names and Rust error text out of responses (a method's database or enqueue error is a generic 500; the cause is in the server log). *Limits.* No handler time limit and no rate limit in this version: a slow method holds a pool connection for as long as it runs, and the task is not cancelled when the client disconnects, so long work belongs in a job. Inbound webhooks use a method and an API token for a user with the narrow role the method needs. Tests: `crates/forgebase/tests/methods.rs` (the whole matrix over HTTP on a real database) and the `http_per_site` scenario of `crates/forgebase/tests/site_apps.rs` (a real server, two sites).

## Outgoing webhooks (M9.2, ADR 0020)

[ADR 0020](../adr/0020-outgoing-webhooks.md). A webhook makes the server open a connection to a URL that an operator chose, so the guards are strict by default and the two exceptions are explicit, per-webhook and visible.

- **SSRF guard: resolve, vet, pin.** The host of the URL is resolved by Forgebase (an IP literal is taken as it is) and **every** address is checked against one blocklist: IPv4 `0.0.0.0/8`, `10/8`, `100.64/10`, `127/8`, `169.254/16` (link-local, with the cloud metadata address `169.254.169.254`), `172.16/12`, `192.0.0/24`, `192.168/16`, `198.18/15`, `224/4`, `240/4`, and as an explicit extra the Azure WireServer `168.63.129.16/32` (reachable from Azure virtual machines, a public address otherwise; M9.3); IPv6 `::/96` (`::` and `::1`), `fc00::/7`, `fe80::/10`, `ff00::/8`, and IPv4-mapped (`::ffff:0:0/96`) and NAT64 (`64:ff9b::/96`) addresses by the IPv4 address inside. One blocked address refuses the delivery, **permanently** (it would fail again). The connection is then made to the vetted addresses only, by a resolver that never looks the name up again, so a DNS answer that changes in between (DNS rebinding) cannot redirect the request. Redirects are **not followed** (a 3xx is a permanent failure), so an allowed host cannot send the request to a blocked one. Tests: every range and its edges, a name that resolves to loopback, IP literals (loopback, private, link-local, the metadata address, IPv4-mapped IPv6), a host name that is only reachable through the address it is given, and a redirect that is not followed (`crates/forgebase/src/webhook_client.rs`, `crates/forgebase/tests/webhooks.rs`). Not on the list, so reachable: documentation ranges and IPv6 transition prefixes other than the two named; any **port** is allowed (the address rules are what protect the network).
- **`allow_private` is a risk flag.** A webhook added with `--allow-private` may reach loopback, private, link-local and reserved addresses, **the metadata service included**. It exists for a receiver inside the operator's own network and for tests. Whoever can run `forgebase webhook add` can already read the database; but a deployment that runs `webhook` commands from a less trusted place should not allow the flag. `list` shows it.
- **`insecure_http` is a risk flag.** It allows `http://`: the payload (a full document snapshot) and the signature travel unencrypted, and a network attacker can read them and replay a delivery inside the timestamp window. Development only. `list` shows it, and `add` prints a warning. Without it an `http://` URL is refused when the webhook is added and again at every delivery.
- **No credentials in a URL.** `user:password@` is refused (the URL would be logged and leaked); a token goes in the path or the query, or better, the receiver verifies the signature.
- **Secrets.** The signing secret is 32 random bytes (hex) from the operating system, or read from standard input (at least 16 bytes, M9.3), and is **stored in plain text** in `fb_webhook.secret` because HMAC needs the key: anyone who can read the database (or a backup of it, see below) can read every secret and forge deliveries. `add` and `rotate-secret` print a generated secret **once**; `list`, every error message and the log never show it (the `Debug` of a webhook omits it and its URL). A URL often carries a token, so messages, the job's `last_error` and the worker's log name only the scheme, host and port and the status, never the path or the query. Tests: the CLI output of `add`, `list`, `test` and refused commands, the `last_error` of failed deliveries, and the formatting functions.
- **The snapshot is the full document, not filtered by permissions.** A delivery carries every field and child row of the document as stored, whatever the permissions of the user who made the change: the webhook is configured by an operator for a system the operator chose, not for a user. Do not point a webhook at a receiver that the data's audience may not see, and remember that a field marked as hidden to some roles in the permission rules is **not** hidden here. A snapshot over 64 KiB is sent without its data (`"truncated": true`), and so is one that cannot be written as JSON (`"unavailable": true`, M9.3): a webhook never makes a write fail.
- **Signature.** `HMAC-SHA256(secret, "<timestamp>.<body>")` over the exact body, in `X-Forgebase-Signature`; the timestamp is in the signed text, so a receiver that rejects timestamps older than a few minutes and compares in constant time rejects replays and forgeries ([recipe](../guide/webhooks.md#verifying-a-delivery)). Delivery is at-least-once with the same `X-Forgebase-Delivery` on every retry: the receiver de-duplicates.
- **TLS.** `rustls` with `ring`, the operating system's roots (`SSL_CERT_FILE` honoured), TLS 1.2 and 1.3, the certificate chain and the host name always verified; there is no option to skip verification. A receiver with a private CA needs that CA in the host's trust store.
- **Availability.** A delivery holds a worker's job slot and a database connection for at most 10 seconds; the response is read up to 64 KiB and dropped. A receiver that is slow or down delays only its own deliveries (they retry with a growing delay and then die), never the document operation that caused them.
- **Operators only.** There is no HTTP route or desk screen for webhooks; the `webhook` commands are the trusted local CLI. A hook or an app cannot add a webhook through any API of this version.

## Import and export (M9.3, ADR 0021)

[ADR 0021](../adr/0021-import-and-export.md). Export moves much data out in one request and import writes much data in one request; each has its own right and its own limits.

- **The `export` right and data leaving.** Export needs `read` **and** `export`, deny by default, so reading a list does not give the right to take all of it away: an app grants `export` to the roles that should (a clerk may read an order and still not download every order). Rows follow the read rules in SQL, `if_owner` included (if either right is `if_owner`, only the caller's own documents). A report exports with the report's own roles and limits: **a report has no row-level rules, so exporting it gives exactly what running it gives**. The export is as large as the filters; the limit (`export_max_rows`, 100 000) is checked by a count before the first byte and is a guard against a mistake, not against a user who may export everything and asks in pages: there is no rate limit, as for every other route. An export holds one pool connection and one `REPEATABLE READ` snapshot while it streams, but only as long as the client takes each chunk: a chunk that is not taken within `export_send_timeout` (30 s) aborts the body and releases both. A client that reads slowly but steadily can still take long; put a timeout in the reverse proxy.
- **CSV and formula injection.** A spreadsheet that opens an exported file runs a cell that starts with `=`, `+`, `-`, `@`, TAB or CR as a formula (DDE, `HYPERLINK`, data exfiltration through a web request). A text that a user typed into any field can therefore attack whoever opens the export. The writer prefixes `'` to a **text** value that starts with one of them, always (no switch); it does **not** touch numbers, decimals, dates or booleans, which cannot be a formula, so `-5` stays `-5`. The residual risks: CSV import does not strip the `'` (a text round-trips with it, and JSON keeps exact text); a spreadsheet may treat other leading characters specially (a leading space or a quote is not a formula start); and **this is a mitigation for the person who opens the file, not a validation**: the text is stored as typed. JSON exports are never altered. Tests: `csv_cells_are_quoted_and_text_that_could_be_a_formula_is_prefixed` and the unit tests of `forgebase_http::transfer`.
- **Import and denial of service.** The import route has its own body limit (16 MiB, `import_body_limit_bytes`; the other routes keep 1 MiB) and a row limit (10 000, checked while reading, before anything runs); the rights are checked **before the body is read**, so a caller without the right cannot make the server buffer a file. A file in memory is up to 16 MiB per request and the transaction is long (about 37 s for 10 000 rows, measured): many concurrent imports can use memory, connections and locks. A crafted file cannot make the answer grow: a CSV header with more columns than the DocType can have (its fields, `name` and the standard columns) is refused with one problem before any column is read, and every file-level list of problems has at most 100 entries and an "and N more" line (tested with a header of 100 000 columns). The row limit counts child rows with their documents, so a small JSON file cannot carry millions of rows. The route needs an authenticated user with the import right; keep the right to the few roles that load data, and put a request limit in the reverse proxy.
- **Every row through the pipeline as the caller.** Import is not a back door: hooks, validation, naming, links (resolved with the caller's read rule on the target), workflow rules and the per-row rights of `insert` and `update` all apply, so a row that the caller may not write is a row error and, with all-or-nothing, no row is kept. An upsert needs `write`, and an `if_owner` caller who names a document of somebody else does not see it: the row is an insert, which collides with the existing name.
- **The dry run changes nothing and says so.** `dry_run=1` runs every row, including the hooks, in the one transaction and always rolls it back: no documents, no outbox jobs, no webhook deliveries (tested: the same file for real enqueues them, the dry run does not). A hook that does something outside the transaction would do it on a dry run too; the hook API cannot reach the database, but app code is trusted code. The dry run returns what each row would have caused, including the names it would have chosen: it needs the same rights as the import itself.
- **Errors do not widen what a caller learns.** A row error is the error the document API gives for that row; an unreadable link is reported like a missing one; a file-level error names a column of the caller's own file. The error list has at most 100 entries.

## Multi-site isolation (M7.1, Accepted, ADR 0014)

Decision record: [ADR 0014](../adr/0014-multi-site-database-per-site.md). Design and decisions: [architecture, section 9](architecture.md#9-multi-site-accepted-adr-0014). Security properties (M7.1, and M7.2 where marked):

- **Separate databases.** Each site has its own database and pool; there are no cross-site queries and no global pool or URL. Every database command resolves one site first (`--site`, required when the config file has several) and uses only that site's pool. A row-level tenant column was rejected because one permission bug would leak data.
- **Sessions and tokens are per site.** They live in the site's own database, so a session cookie or API token of site A is refused (`401`) on site B, even for a user with the same name (tested). The session cookie is host-scoped (no `Domain` attribute).
- **The `Host` header chooses the site, and nothing else does.** `X-Forwarded-Host` and `Forwarded` are never read: the reverse proxy must pass the original `Host`. A missing, repeated or malformed `Host` is `400 invalid_host`; with a config file a well-formed host that no site owns is `404 not_found`, without a config file a host outside the allow-list is `400` (DNS-rebinding protection, unchanged). The check runs before routing and authentication.
- **The config file holds no secrets.** The database URL of a site is read from the environment variable the file names; the value is never printed (an unset variable is an error that names the site and the variable). The file is found only by `--config` / `FORGEBASE_CONFIG`, never by searching the current directory, and unknown keys are refused, so a typo cannot silently drop a setting.
- **Absolute-form targets.** A request target with a host (`GET http://host/path`) must name the same host as the `Host` header (case and port ignored), else `400 invalid_host`: the site is chosen by `Host` alone, and a disagreeing target is never answered for the other host.
- **Apps per site (M7.2).** Each site has its own registry, built from the apps its `apps` list installs. A DocType, job or schedule of an app that is not installed on a site is unknown there on every path (command line, HTTP, worker). Removing an app from a site keeps its tables and data; nothing is dropped. A worker serves one site per process, so it claims only that site's jobs, and only those whose names its site's registry knows.
- **Creating a site (`site create`) needs privileges.** `CREATE DATABASE` needs the `CREATEDB` privilege (or a superuser) for the role of the site's URL, and a connection to a maintenance database (`postgres` by default, `--maintenance-db` to change). Give `CREATEDB` only to the role that creates sites, for example by creating the database with a separate admin role (an administrator can create the empty database and run `migrate --site`), and keep the role that `serve` and `worker` use without it. The command refuses an existing database, never migrates it implicitly, and never prints the URL: an error names the site, not the URL (a test checks it).
- **Backups and restores (M7.3).** A backup (`site backup`, `pg_dump`) holds everything in the site's database, **including password hashes, session records and API token digests**: it is as sensitive as the database. The file is created with mode 0600 and never overwrites anything; it is not encrypted by Forgebase, so protect and encrypt it where you store it, and apply your own retention. The database URL and password reach `pg_dump` and `pg_restore` only as `PG*` environment variables (never on the command line, where `ps` shows them), other inherited `PG*` variables are removed, and no message contains a URL or a value of it (a URL option that cannot be passed on is named, not shown). A restore goes only into an **empty** database (a conservative check; it never merges into existing data), runs in one transaction, and the client tool must have the server's major version and the dump must not be newer than the server. `CREATEDB` is needed only to create a database (`site create`, including `--empty`): an administrator can create the empty database by hand, owned by the application role, which never needs `CREATEDB`. See the [operations guide](../guide/operations.md#backups).

## Secrets

Config file and environment variables only; never in DB metadata or logs. (The config file names the variables and holds no secret; a backup file does hold secrets, see above.) Session tokens and API secrets are stored hashed. Forgebase never logs them, but PostgreSQL may log bind parameters; see the known limits above. The database URL holds the password: no error message or log line of Forgebase contains the URL, and the TLS settings are read from it without printing it ([ADR 0018](../adr/0018-postgres-tls.md)); keep it in the environment (a secret variable of the host), never in a committed file.

## The command-line tool (M1.3)

`forgebase` is a **trusted local tool**: whoever can run it with a database URL has full access to that database, including creating users, setting passwords and creating API tokens (`forgebase user ...` and `forgebase token ...`, M3.1; passwords are read from standard input, never from an argument or environment variable, and `token create` is the only output of a secret). It has no authentication, and its `doc` commands run as the **system context** (`Caller::System`, M3.2), to which no permission rule applies; real users and their permissions apply to the HTTP API (M3.3). `--actor` names the system actor that is recorded in `owner` / `modified_by` on insert and update (and, for `doc transition`, in the workflow log, with no check of the transition's roles) (on delete it is given to hooks and not stored); it is not verified and must not be treated as an identity. The database URL (with its password) is read from the `FORGEBASE_DATABASE_URL` environment variable, never from a command-line argument, and is not printed. Input is checked before any SQL runs (JSON mapping, then core validation), and a datetime whose UTC instant is outside the supported range is an error, not a panic.

## Audit

`owner`, `modified_by`, `modified_at` from day one. Full version history is deferred.

## Deferred items

OAuth/SSO, 2FA, field-level permissions, user permissions, sharing, full audit/version history, workflow-based edit restrictions, Postgres row-level security as defense in depth (idea only, not planned).

- ~~Permission-aware Link name resolution.~~ Answered in M3.2 (owner decision 9, ADR 0011): a Link is resolved with the caller's read access on the target DocType, and a target the caller cannot read gives exactly the `LinkNotFound` of a missing one; `LinkedDocumentExists` names the referencing DocType only to a caller who can read it. Remaining, accepted limit: unique violations and `AlreadyAmended` can still reveal existence.
- ~~Read-only database role and `FOR KEY SHARE`.~~ Settled in M3.2 as a **non-goal**: Link lookups and locking reads need the `UPDATE` privilege on the table, so a read-only role cannot run the write operations; it is not used. Reports (later) must be designed around it.

## Required negative tests

Per the testing strategy in [maintenance-policy](maintenance-policy.md#testing-strategy), M3 is not complete without explicit negative tests. Status after M3.3: every item below that can exist today is implemented and tested against PostgreSQL; the multi-site item waits for multi-site, and custom endpoints (`/api/v1/method`) are not implemented (a request to them is a 404).

- every permission rule: a user without the role is denied (read, write, create, delete, submit, cancel, amend), and a DocType with no rules is denied to non-admins. *Tests:* `forgebase-db/tests/permissions.rs` (every right with and without its role, deny by default, union of roles); over HTTP `forgebase-http/tests/resources.rs` (`the_authorization_matrix_over_http`, `the_lifecycle_and_its_error_codes`);
- "owner only": another user's document is neither listed nor fetchable. *Tests:* `permissions.rs`, `list.rs`; over HTTP `if_owner_hides_the_documents_of_others` (404 for get, patch and delete, absent from the list, filters do not reveal it);
- list queries never return rows the user cannot read (including via filters, sorting and paging). *Tests:* `forgebase-db/tests/list.rs`; over HTTP the `if_owner` test above and `listing_filters_sorts_and_pages`;
- injection attempts in filters, field names, sort keys and DocType names are rejected or inert. *Tests:* `list.rs`; over HTTP `injection_attempts_are_inert` (hostile DocType path segments are 404, hostile filter and sort keys are 400, hostile values are inert);
- expired, revoked and tampered session tokens and wrong API secrets are rejected. *Tests:* `forgebase-db/tests/auth.rs`; over HTTP `forgebase-http/tests/auth.rs` (`expired_unknown_and_tampered_cookies_are_the_same_401`, `bad_tokens_are_the_same_401`, `a_disabled_user_loses_the_session`, `logout_ends_the_session_and_clears_the_cookie`, `lockout_works_over_http`, `a_failed_login_is_the_same_401_for_every_reason`);
- state-changing cookie-authenticated requests without a valid CSRF token are rejected. *Tests:* `a_cookie_session_reads_and_needs_csrf_to_change_things` (missing, wrong, another session's and malformed token; POST, PATCH and DELETE; the logout case is in `logout_ends_the_session_and_clears_the_cookie`), `an_api_token_needs_no_csrf`, `the_authorization_header_wins_over_the_cookie`;
- `Host` validation, no CORS, uniform errors (for every failure that reaches the router; hyper-level errors such as `431` or malformed HTTP bypass the envelope) and no leaked secrets. *Tests:* `the_host_is_checked_first_on_every_route`, `a_repeated_host_header_is_refused`, `configured_hosts_are_used_and_ipv6_works`, `no_cors_headers_anywhere`, `every_kind_of_failure_uses_the_envelope`, `the_body_limit_is_413_in_the_envelope`, `no_secret_appears_in_a_response_except_where_it_is_issued`, `internal_errors_are_generic`, `a_unique_violation_does_not_echo_the_key`, `concurrent_logins_are_bounded` (timing based) and, in `forgebase-http/src/lib.rs`, the deterministic `a_login_over_the_bound_is_503_without_touching_the_database` and `login_permits_never_take_every_connection`; decision 9 over HTTP: `decision_9_no_leaks_through_links`;
- custom endpoints without a declared permission are refused: a method with neither `.roles(..)` nor `.any_user()`, with both, or with an empty role list is a startup error (M9.1; `a_method_needs_exactly_one_kind_of_access_and_a_valid_unique_name` in `crates/forgebase/tests/methods.rs`), and the matrix of calls (no session, CSRF, wrong role, right role, Administrator, `any_user`, unknown and uninstalled methods) is `the_gate_is_authentication_csrf_and_the_roles` and `the_methods_of_an_app_that_is_not_installed_do_not_exist` there;
