# Desk

The desk is a React + TypeScript app in `desk/` (no UI component library; at runtime only `react`, `react-dom` and the self-hosted Inter font). `forgebase serve` serves the **built** desk on the same origin when `FORGEBASE_DESK_DIR` is set (unset: no desk, `/desk/*` is a 404). It has a login page, a home of cards per app, a sidebar of the DocTypes the user can read grouped by app, breadcrumbs, a **list view** per DocType (the title of each document, the columns the DocType file chooses, a status badge, a quick search, filters that apply as you change them, paging, sorting) and a **form view** generated from the DocType metadata: native controls per field type (a Link field suggests names as you type, a Table field is a grid of rows), Save (only the changed fields are sent), and for a submittable DocType the **Submit**, **Cancel**, **Amend** and **Delete** buttons, shown only when the user has the right and the document's status allows it (the API enforces every right again). Field errors of the server are shown on the fields, a version conflict offers a Reload and keeps your edits, and leaving a form with unsaved changes asks first. Save is the main action (Ctrl/Cmd+S works too), Submit is the main action of a saved draft, and Cancel, Amend and Delete are in a More menu and ask first; a toast confirms what was done. The look is a navy corporate theme (the colour of the logo banner) built with Tailwind CSS v4 at build time (a development tool: the shipped desk is one static CSS file and the build is unchanged, `npm ci && npm run build`; [ADR 0017](../adr/0017-desk-styling-tailwind.md)); the layout works from 320 px up.

**UX.4: the desk polish.** A smoother, more elegant look on the same navy base: Inter (self-hosted, Latin subset, OFL-1.1, [ADR 0017](../adr/0017-desk-styling-tailwind.md)), filled inputs, pill badges, soft cards and 150 to 200 ms CSS motion that `prefers-reduced-motion` switches off. A slim top bar has a search field that opens the **command bar** (Ctrl/Cmd+K: jump to a DocType, create a new document, or reopen one of the last ten documents opened in the tab; navigation only, nothing is stored). The sidebar shows an icon per DocType: a DocType may name one with `icon = "file-text"` in its file (the allowed names are in `crates/forgebase-core/src/doctype_icons.txt`; the icons are copied from [Lucide](https://lucide.dev) (ISC) into `desk/src/icons.tsx`, with the licence notice in `desk/src/icons/LICENSE-lucide.txt`, and are **not a dependency**). The list is one card with the search, a chip for each active filter that you can remove, a count, the owner's initials and a relative "Modified" time (the exact time on hover); the form has a Details card, a card per table and an info panel (created by, last modified, version); a read-only value is plain text. A Link shows the target's title (for example the customer's full name) when the target DocType has a `title_field` and you may read it, through `GET /api/v1/resource/{doctype}?link_titles=1` ([architecture, section 7](../blueprint/architecture.md#7-api-rest-resource-api-implemented-in-m33-metadata-and-session-routes-in-m41-the-rest-proposed)).

**UX.5: soft neutral.** A corporate refinement of the look, with the same navy and the same behaviour: a neutral grey scale, softer text, flat cards, borderless filled fields (white with a visible keyboard ring on focus) and a child table drawn as one grid of plain cells; the one accepted accessibility trade-off (the boundary of a filled field, WCAG 1.4.11) is in [ADR 0017](../adr/0017-desk-styling-tailwind.md), section "UX.5".

**M8.2: the workflow in the desk.** For a DocType with a `[workflow]` the badge and the list's Status column show the workflow state (in the colour of its `style`), the plain Submit and Cancel buttons give way to the actions you may take now (the first is the main button, a third and later ones are in the More menu; each asks to confirm, and is disabled while the form has unsaved changes), and the info panel has an **Activity** timeline of the transitions, newest first. The list can filter by state.

**M8.3: saved views, columns and the summary.** The list toolbar has three buttons. **Views** saves the filters, sort order and columns of the list under a name and opens them again (a view is **private** to the user who saved it: nobody else sees it; an Administrator can also save one **shared** with everyone who can read the DocType). **Columns** chooses the columns to show (kept in the address, so a reload keeps them). **Summary** opens a panel that groups the documents by a field (the status, the owner, a select field, ...) with the count and the sum, average, minimum or maximum of up to three number fields; a click on a group filters the list to it. The summary counts only what the user may read, as the list does. The routes are `GET`, `POST`, `PATCH` and `DELETE /api/v1/views/<doctype>` and `GET /api/v1/summary/<doctype>?group_by=FIELD&aggregates=sum:amount` ([architecture, section 7](../blueprint/architecture.md#7-api-rest-resource-api-implemented-in-m33-metadata-and-session-routes-in-m41-the-rest-proposed) and [section 11](../blueprint/architecture.md#11-desk-reports-workflow)).

**M8.4: query reports.** An app can define a **report**: SQL that is compiled into the binary (like an app migration), run for the roles you name, with typed parameters. `App::report("sales_by_customer", Report::sql(include_str!("../reports/sales_by_customer.sql")).roles(&["Sales Manager"]).param(Param::date("from").required()).column(Column::decimal("total")))`. The parameters are `$1..$n` in the order you declare them and are always bound, never pasted into the SQL; the columns are the ones the statement returns, in order. A report runs in a **read-only transaction** with a 30 second timeout and a 10 000 row limit (each can be changed, up to 300 s and 100 000 rows), so a statement that writes fails and a runaway one is stopped. **Row-level rules do not apply inside a report**: it shows what its SQL selects to every role that may run it, so give it only to roles that may see all of that data. A user without one of the roles gets "not found", and the report is not listed for them. `forgebase migrate` checks every report's SQL against the database (parameter and column counts and types) and exits 1 on a mismatch. The desk has a **Reports** section in the sidebar and in the command bar; a report page has a parameter form, a **Run report** button and a result table you can sort by clicking a column header (the parameters are kept in the address, so a reload runs it again). The API is `GET /api/v1/report` (the reports you may run) and `POST /api/v1/report/{app}.{name}` with `{"params": {...}}`. There is no CSV export and there are no charts yet. Design and limits: [ADR 0016](../adr/0016-query-reports-read-only-execution.md) and the [security model](../blueprint/security-model.md#query-reports-m84-adr-0016); the [guide](workflow-and-reports.md) has the full section.

**M9.3: export and import.** A list has an **Export** menu (CSV or JSON) for a user who has the `export` and `read` rights: the file holds the list as it is shown, **the current filters and sort** and the shown columns (with the title the Name column shows), as one download of `GET /api/v1/export/<doctype>` (a plain link: the browser downloads it; a list over the limit of 100 000 rows is refused by the server, and because the browser saves what it is given, such a refusal shows as a failed download rather than a message: narrow the filters first; the CSV it writes imports again, since the standard columns it contains are ignored). A user who has `import` and `create` also sees an **Import** button, which opens `#/import/<doctype>`: choose a CSV or JSON file (the format is taken from its name and can be changed), the mode (insert, or update by name, which needs the `write` right), and press **Validate**. Validate is a dry run: it reads every row through the same pipeline as the real import and keeps nothing, then shows either "No errors" with the counts, or a **table of the rows with errors** (row, line, name, message; the first 100). **Import** is off until the file, the format and the mode you validated are the ones you have now and the validation had no errors; it sends the file again and shows the counts with a link back to the list. If the data changed in between and a row now fails, nothing is imported and the errors are shown. A report's result has an **Export** menu too: it runs the report again with the same parameters and saves the file ([ADR 0021](../adr/0021-import-and-export.md), [HTTP API](http-api.md#import-and-export-m93), [CLI](cli.md#data-commands-export-and-import-m93)).

```sh
# Build the desk (Node.js ^20.19.0 || >=22.12.0; desk/.npmrc ignores dependency install scripts): writes desk/dist
cd desk && npm ci && npm run build && cd ..

# Run it with the API from the [HTTP API guide](http-api.md) (a user and the tables must exist), then open http://localhost:8000/desk/
# FORGEBASE_DEV_INSECURE_COOKIES=1 is for plain HTTP on localhost only; behind HTTPS leave it out.
FORGEBASE_DEV_INSECURE_COOKIES=1 FORGEBASE_DESK_DIR=desk/dist cargo run -p sales -- serve

# Develop the desk with hot reload (proxies /api to a running `forgebase serve` on port 8000): http://localhost:5173/desk/
cd desk && npm run dev
```

The desk keeps no secret in the browser except the HttpOnly session cookie: the CSRF token lives in memory and is recovered after a reload with `GET /api/v1/session`. What the desk may show is decided by `GET /api/v1/meta` and `GET /api/v1/meta/{doctype}` (only DocTypes the user can read, with the user's rights); the API enforces every right again. A document named `.` or `..` cannot be opened in the desk (a browser resolves those path segments before the request is sent); every other name is URL-encoded. The routes, the form view design, the static-serving rules and the Content-Security-Policy are in the [architecture](../blueprint/architecture.md#11-desk-reports-workflow) and the [security model](../blueprint/security-model.md#the-http-layer-implemented-in-m33).

**Smoke test.** Playwright tests (Chromium) drive the built desk against a real server: login, home, list, search, create, save, edit and submit a sales order, the More menu, no horizontal scroll at 375 and 320 px, a user without the submit right, and (UX.4) the command bar, a filter chip, the link title and reduced motion, and (M8.2) a purchase request that a clerk sends for approval and a manager approves, and (M8.3) a private and a shared saved view, the Columns menu and the Summary panel (CI job `e2e`). To run it locally you need a PostgreSQL 16 server, an **empty** scratch database, the built desk and Chromium:

```sh
export FORGEBASE_DATABASE_URL=postgres://forgebase:forgebase@localhost:5432/fb_e2e   # an empty scratch database
cargo build -p forgebase --example e2e_app && (cd desk && npm ci && npm run build)
desk/e2e/seed.sh                                   # migrates, creates the users e2e_manager and e2e_clerk, a customer and the e2e-only DocType purchase_request (with a workflow) (the example binary `e2e_app`, which has one app with a query report, and `--doctypes`: it adds a role that only the e2e test uses)
FORGEBASE_DEV_INSECURE_COOKIES=1 FORGEBASE_DESK_DIR=desk/dist target/debug/examples/e2e_app serve --doctypes target/e2e/doctypes &
cd desk && npx playwright install chromium && npx playwright test   # or set PLAYWRIGHT_CHROMIUM_EXECUTABLE to an installed Chromium
```

**Screenshots.** `desk/e2e/screenshots.spec.ts` adds a few sample documents (draft, submitted and cancelled orders) and takes the login page, home, list and form at 1280, 800 and 375 px (and the list at 320 px, a submitted form at 375 px); it also checks that no page scrolls sideways on a phone. It is skipped unless `SCREENSHOTS=1`, so CI does not run it, and the images are not committed:

```sh
cd desk && SCREENSHOTS=1 SCREENSHOT_DIR=/tmp/desk-shots npx playwright test screenshots   # same server and database as the smoke test
```
