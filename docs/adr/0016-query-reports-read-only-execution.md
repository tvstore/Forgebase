# 0016 Query reports: app-defined SQL, read-only execution

- Status: Accepted (owner decisions 8 and 9 of the M8 plan, 2026-10-30); implementation details of M8.4 are separated below and are not owner decisions. Updates the public surface of [ADR 0012](0012-app-model-and-public-api-boundary.md#public-surface-update-m84) and relies on the role model of [ADR 0011](0011-permission-model-phase-1.md).
- Date: 2026-10-30

## Context

A business application needs numbers that no single DocType list shows: sales by customer, receivables by age, stock by warehouse. The group-by summary of M8.3 covers one DocType and one field. Frappe has Query Reports (SQL), Script Reports (Python) and a Report Builder; the [feature matrix](../blueprint/feature-matrix.md) lists them, and the [architecture](../blueprint/architecture.md#11-desk-reports-workflow) left SQL reports Proposed for M8.4.

The difficulty is trust. A report is arbitrary SQL, so it cannot go through the document permission layer ([ADR 0011](0011-permission-model-phase-1.md) turns a rule into a `WHERE` clause on one DocType; it cannot rewrite a join over five tables). The framework's rule against admin-authored code stored in the database ([architecture](../blueprint/architecture.md#what-we-deliberately-do-not-build)) also stands. The owner approved the M8 plan on 2026-10-30; decisions 8 and 9 are the ones recorded here.

## Decision

1. **Reports are app-defined SQL, limited by role** (owner decision 8). An app declares a report with `App::report(name, Report::sql(..).roles(..).param(..).column(..))`. The SQL is compiled into the binary (`include_str!`), so it is **trusted code, like an app migration**: it is written by a developer, reviewed in a pull request and shipped with the binary. Nothing is stored in the database and nothing is editable at run time.
2. **Typed parameters, always bound.** A report declares its parameters (`data`, `int`, `decimal`, `date`, `check`, `link`, `select`) and its result columns (`data`, `int`, `decimal`, `date`, `datetime`, `check`, `link`). Both are **positional**: `$1..$n` are the declared parameters in order, and the statement returns the declared columns in order. A parameter value is checked like the field of the same kind and then bound; it is never put into the SQL text. An absent optional parameter is bound as `NULL`, so the SQL handles it: `($3::text IS NULL OR customer = $3)`.
3. **Access is by role only.** A report names at least one role (an empty list is a startup error: there is no "any user" report, which keeps deny by default). The Administrator role and the system context always pass. A caller without a role gets **404**, the same as for a report that does not exist, and the report is not in `GET /api/v1/report` for them.
4. **Read-only, with a time limit and a row limit** (owner decision 8). A report runs in a `READ ONLY` transaction with `SET LOCAL statement_timeout` (default 30 s, at most 300 s per report) and `SET LOCAL lock_timeout` (5 s), and returns at most `max_rows` rows (default 10 000, at most 100 000 per report); one more row than that only sets `truncated`. A statement that writes fails with SQLSTATE 25006, a slow one with 57014.
5. **Row-level rules do not apply inside a report.** The SQL shows what it selects, to every role that may run it. This is the main security consequence of the decision and is repeated in the [security model](../blueprint/security-model.md#query-reports-m84-adr-0016). The caller is **not available to the SQL** in M8 (there is no `$caller` parameter), so a report that must filter by user cannot; in M8 a report is for roles that may see all the rows it selects.
6. **The SQL is checked when `migrate` runs.** After the app migrations, `migrate` **prepares** every report of the site's apps (a parse and type check, nothing runs) in a read-only transaction and refuses a report whose parameter count, column count, column types or parameter types do not fit what it declares. The error names the report and the problem.
7. **API and desk** (owner decision 9: no CSV export and no charts in M8). `GET /api/v1/report` lists the reports the caller may run, with their parameters and columns, never the SQL; `POST /api/v1/report/{app}.{name}` runs one. The desk has a Reports section in the sidebar, "Run <report>" commands in the command bar, and a page with a parameter form and a sortable result table.

## Implementation details (M8.4)

These choices were made while implementing M8.4 and are reviewed with that change; they are not owner decisions.

**Where things live.** `forgebase-core::report` has `ReportDef`, `ReportParam`, `ReportColumn` and the two kind enums: plain data, the checks that need no database (`ReportDef::problems`) and the parameter checks (`ReportDef::bind_params`, which reuses the vocabulary and messages of document validation). `permission::can_run_report` is the access decision, next to `evaluate`; nothing else compares a report's roles. The `Registry` holds the reports by full name next to the DocTypes and the job names, so each site has exactly the reports of its installed apps (the M7.2 rule: `compose` runs on the site's apps). `forgebase-db::reports` runs a report (`run_report`), checks the statements (`check_reports`) and finds the titles of Link columns (`report_link_titles`). `forgebase-http::reports` has the two routes. The `forgebase` crate has the builders `Report`, `Param` and `Column`, `App::report`, and `testing::check_reports`.

**The builders** are `#[non_exhaustive]` with private fields and chaining methods, like `JobOptions` and `Schedule`. Labels default to the humanized name. A trailing `;` and whitespace are stripped from the SQL when the app is composed. Limits above their caps and every other mistake are **startup errors**, collected with the other app problems: an invalid or duplicate report name, no roles (or an invalid role), no columns, empty SQL, a duplicate or invalid parameter or column name, a Select without options or with duplicates, a default value that does not fit its parameter, a limit above its cap, and a Link parameter or column whose DocType is unknown, a child DocType, or belongs to an app that this app does not depend on (the rule of Link fields, so a report works on every site that installs the app). A report cannot link to the DocTypes of the `--doctypes` directory.

**Parameter values.** Data and Link are text of at most 140 characters without NUL; a required text may not be blank; a Select value must be one of the options; Int, Decimal, Date and Check take their own kind. A parameter that is absent gets its default (`Param::default_value`), an explicit `null` does not. Link values are only bound: they are **not** checked for existence, and the caller's read rules do not apply to them. Every problem is reported per parameter in the usual `422 validation_failed` details (`field `from` is required`), and an unknown key is refused. The checks that need only the JSON (a wrong kind) run while the body is mapped, the rest in `bind_params`.

**Binding.** The type of a placeholder is what PostgreSQL infers for it, never the value's. An integer fits `int2`, `int4`, `int8` and `numeric` (a value out of range is a database error, not a wrap); a decimal fits `numeric`, a date `date`, a check `bool`; a placeholder inferred as `text`, `varchar` or `unknown` takes **any** kind as the text form of the value, so `$1::text` always works. A report whose placeholder has another type (a `$1::uuid`) fails.

**Execution.** One `READ ONLY` transaction, the two `SET LOCAL`s, and then the statement is **prepared, bound and run through a portal that returns at most `max_rows + 1` rows**, so the server stops producing rows after the limit and the SQL is not wrapped. (The plan sketched `SELECT * FROM (<sql>) LIMIT n`; a data-modifying `WITH` cannot sit inside a subquery, so a wrapper would turn the read-only refusal of such a statement into a different error. The portal gives the same limit with the statement run as written.) Before it runs, the prepared statement's parameter and column counts are compared with the declaration, so a statement that was never checked (a `COMMIT`, a wrong column count) is stopped; the transaction is always rolled back at the end. The `SET LOCAL`s end with the transaction, so a pooled connection never keeps a timeout.

**Errors.** `57014` (statement timeout) and `55P03` (lock timeout) are `DbError::ReportTimeout`, HTTP **504** `report_timeout`: "the report took too long; narrow the parameters". `25006` is `DbError::ReportReadOnly`: a mistake of the app, so HTTP 500 `internal` with the report's name in the server log and nothing in the response. A statement whose shape does not match the declaration is `DbError::Report`, also 500. Any other database error takes the existing internal-error path. **The SQL text is never in an error response or any other response**; it is not in the list either. The server's own log (standard error) may carry the database's error message, which can quote a fragment of the statement (for example `syntax error at or near …`).

**The check at `migrate`.** `forgebase_db::check_reports` prepares each statement inside one read-only transaction with a savepoint per report (a statement that fails to prepare aborts the transaction, the savepoint lets the next one be checked). It reports: the SQL does not prepare (the database's message: an unknown column or table); a parameter count different from the declared one; a column count different from the declared one; a column whose type does not fit (`int2`/`int4`/`int8` for int, `numeric` for decimal, `text`/`varchar`/`bpchar` for data and link, `date`, `timestamptz` for datetime, `bool` for check); and a parameter whose inferred type does not fit its kind (int: the integer types and `numeric`; decimal: `numeric`; date: `date`; check: `bool`; data, link and select: `text` or `varchar`), with the **lenient rule** that a parameter inferred as `text` or `unknown` fits every kind. It does not run in a dry run (nothing is applied, so the tables a report reads may not exist). `testing::check_reports(&Forgebase, &TestDb)` runs the same check, and `TestDb::migrate` runs it like the command. The desk and API list a report whether or not it passed: it is the migrate error that stops the release.

**Known limitation: the check runs after the migrations commit.** A report reads the tables the migrations create, so it can only be checked once they exist. When the check fails, `migrate` exits 1 with the problems and "fix the report and run migrate again", but the schema sync and the app migrations of that run **stay applied** (the output says so). Running `migrate` again is safe: nothing is applied twice, and it checks again. A deploy script must treat exit 1 as a failed release. The alternative, checking inside the migration transaction, was not chosen because it would roll back unrelated, correct migrations for a mistake in one report and because reports are not versioned like migrations.

**HTTP.** `GET /api/v1/report` returns `{"data": [{"name", "app", "label", "params": [{"name", "label", "kind", "required", "default", "doctype"?, "options"?}], "columns": [{"name", "label", "kind", "doctype"?}]}]}`, by label in byte order. `POST /api/v1/report/{app}.{name}` takes `{"params": {..}}` and returns `{"data": {"columns", "rows": [[..]], "truncated"}}`; a row is an array in column order, in the JSON forms of the documents (decimals as strings, dates `YYYY-MM-DD`, datetimes RFC 3339 in UTC). Errors: 401, 403 `csrf_failed` (cookie sessions; an API token needs none), 404 (unknown, not allowed, or an app that the site does not install), 422 (parameters), 504, 400 and 413 and 415 as for every body. The access check happens **before** the body is mapped, so a caller without the role learns no parameter name. `?link_titles=1` adds the `link_titles` key of UX.4 for the Link columns, under the **caller's read rules** (the same code as the lists; a target the caller cannot read gets no entry; at most 500 distinct names per target DocType are resolved).

**Desk.** The Reports section of the sidebar (icon `clipboard-list`, hidden when there are none) and the "Run <label>" entries of the command bar (a Reports group, matched on label and name) use the list from `GET /api/v1/report`. The page `#/report/<app>.<name>` has the breadcrumb Reports / label, a Parameters card whose controls are the field controls of the same kind (a Link has its picker), required markers, and "Run report". The parameters are kept in the address, so a reload or a shared link shows them and runs the report again; a bare address never runs by itself. The result card has sticky headers, right-aligned numbers, formatted dates, client-side sorting by a click on a header (ascending, descending, back to the order of the SQL; numbers, decimals and dates by value, text with `localeCompare`, empty values last in both directions), the row count, the note when the result was cut at the limit, an empty state and a loading skeleton. A `422` is shown on the parameter fields, a `504` as "The report took too long. Narrow the parameters.", other errors in the alert. On a phone the table scrolls inside its card.

**Tests.** `forgebase-core` unit tests (every definition problem, the parameter checks); `forgebase-db/tests/reports.rs` on a real PostgreSQL (the role gate, parameter problems, **SQL injection**, **write attempts** with a data-modifying CTE, `UPDATE` and `INSERT` that leave the rows unchanged, the **timeout** asserted on the error and on the connection being usable afterwards, the **row limit**, every column kind, every parameter kind, the static check); `forgebase-http/tests/reports.rs` (each status code, the envelopes, CSRF, the body limit, link titles under the read rules, the SQL in no response); `forgebase/tests/reports.rs` and `app_binary.rs` (the public builders, the failing check with the migrations kept, the reports of an app that is not installed); Vitest for the pure desk modules; the Playwright smoke test and the screenshots on the example binary `crates/forgebase/examples/e2e_app.rs`, an app with one report that the stock binary cannot have.

## Alternatives considered

- **Script reports** (Python in Frappe): rejected. Code stored in the database is excluded by the guiding principles, and Rust code in the binary is already available as a job.
- **A no-code report builder:** later. It needs a query model, joins and a permission story; the group-by summary covers the common single-DocType case.
- **Reports through the document permission layer:** impossible for arbitrary SQL. A rule is a `WHERE` on one table; a report is a statement over many.
- **Named parameters (`:from`):** rejected. They need the SQL parsed (to tell a parameter from a string literal or a cast), which is the one thing this design avoids; positional `$n` is what the database already understands.
- **Wrapping the statement in `SELECT * FROM (<sql>) LIMIT n`:** not chosen, see Execution above.
- **A separate read-only database role:** rejected for M8. The [security model](../blueprint/security-model.md) settled that a read-only role cannot run the framework's own operations; a read-only transaction gives the same refusal of writes per report, without a second connection pool and role to operate. It does not stop a report from reading a table the application role can read, which is why the SQL is trusted code.
- **Row-level rules inside a report** (`$caller`, an owner filter): not in M8. It needs the caller in the SQL and a convention that cannot be enforced; revisit with a real need.

## Consequences

- **A report is as trusted as a migration.** It can read every table the binary's database role can read, rules ignored. Review a report like any other code that touches the data; give a report only to roles that may see everything it selects.
- Reports cannot filter by the signed-in user in M8.
- The public API grows by `Report`, `Param`, `Column` and `App::report` (all `#[non_exhaustive]` or built by methods) and `testing::check_reports`; see [ADR 0012](0012-app-model-and-public-api-boundary.md#public-surface-update-m84).
- `migrate` can exit 1 after it applied migrations; the message says so.
- No CSV export and no charts (owner decision 9); an export is M9.3.
- A report SQL error that the check cannot see (a runtime cast failure, a value out of range) is a 500 with the cause in the server log.
- The desk loads the list of reports once after login; a role change shows after the next login.
